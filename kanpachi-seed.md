# The Kanpachi Seed

**A seed introduces people to each other. Once the tunnel is up, it steps out of the way.**

This document explains what the seed does, what it can see, what it stores, and what it can never
learn. It also says what a *hostile* seed could do differently, because the seed is the one part of
Kanpachi that runs on somebody else's machine.

It is written in English for the same reason as
[`kanpachi-protection.md`](kanpachi-protection.md): it is linked from the app and from the public
repositories, and it stays at the repository root because those links are URLs. This one explains;
to put a seed up, the guide is [host your own seed](docs/public/host-a-seed.md), and the
endpoint-by-endpoint reference is [`registry/API.md`](registry/API.md). Kanpachi's design documents
are in Spanish and live in [`docs/`](docs/).

---

## What a seed is

A seed is a meeting point. It is a small server anyone can run (the whole thing installs with one
command on a Linux box), and it is made of two processes:

| Process | What it is | Where it listens |
|---|---|---|
| `easytier-core` | the network engine, running as a public node | a TCP and a UDP port, open to the internet |
| `kanpseed` | the room registry: invite codes, room cards, member counts | HTTP, normally behind the machine's own reverse proxy |

The engine runs with `--no-tun`, so the seed has **no virtual interface of its own**. It is not a
member of anybody's room. It is a switchboard, not a participant.

Both units are generated by `kanpseed init` and can be read in
[`registry/setup/units.go`](registry/setup/units.go).

## What the seed does

1. **It mints invite IDs.** Eight characters out of a frozen 32-symbol alphabet (40 bits), with a
   rate limit in front so that walking the space is not worth the trouble.
2. **It resolves them.** Paste `A7K2-M9QX@seed.example.com` and the client asks that seed, and only
   that seed, which room it means. The same eight characters on two seeds are two different rooms.
3. **It holds a room card it cannot read.** The card carries the room name and the host's nickname,
   sealed with AES-GCM under a key that travels in the *fragment* of the invite link, the part of a
   URL that browsers never send to the server. The seed stores it, serves it, and never sees inside.
   **The seed is not the one doing the sealing**: the host seals the card before uploading it, so a
   modified seed cannot decide to keep a readable copy. A readable copy never arrives.
4. **It counts heads.** It asks its own engine how many peers are in each rendezvous network, over a
   loopback-only RPC port. That answer has peer IDs and addresses in it, and no nicknames. The
   nicknames are inside the encrypted card and inside the encrypted room.
5. **It introduces peers**, so the two ends can punch a hole through their routers and talk
   directly.
6. **It relays, when a direct path cannot be built.** See below.

## Direct, and when it is not

Kanpachi tries for a direct peer-to-peer tunnel between every pair of machines. When it gets one,
which is the normal case, **the seed is no longer in the path**. Your game traffic goes from your
router to your friend's router. The seed does not see it, cannot count it and cannot delay it.

Some networks cannot be punched through. Symmetric NAT is the usual reason, and it is a property of
somebody's router, not a setting anyone chose. For those, the engine falls back to **relay**: the
packets travel through the seed, because that is the only path left.

When that happens:

- **The packets stay encrypted end to end.** A room's real network secret is random, generated by
  the host, and it is never sent to the seed. The host admits guests with a revocable credential
  rather than with the secret, so even a guest cannot hand it over. The seed forwards bytes it
  cannot decrypt.
- **What the seed can see is the outside of the envelope:** that two addresses are exchanging
  packets, how many, how big, and when.
- The app says so. A room where somebody is arriving by relay shows as **degraded**: that is what
  the word means there, and it is recomputed from the live peer table rather than remembered.

## What the seed never receives

- **The room's network secret.** The host generates it, and it stays there.
- **The room name and the host's nickname in the clear.** They are in the encrypted card.
- **Any account.** There are none in Kanpachi. You sign up for nothing, so there is nothing to look
  up later.
- **Which game you are playing, or which ports were opened.** That decision lives entirely on the
  host machine, in its firewall, and is never sent anywhere.

## What the seed in this repository stores

The registry keeps one record per live room, in memory and mirrored to `rooms.json` so that a
restart does not lock out everybody who already has a code
([`registry/store.go`](registry/store.go), [`registry/persist.go`](registry/persist.go)):

| Field | What it is |
|---|---|
| host key | the host's public key, so that reopening the same code cannot be hijacked by an ex-member |
| card | opaque bytes, at most 512 of them, encrypted with a key the server never gets |
| network | the name of the *rendezvous* network, used to count members |
| two timestamps | when the entry expires if nobody republishes, 21 days out, and when its host closed it, zero while it is open |

That is the whole record. Run it and it looks like this (one room, sealed card, no addresses
anywhere):

```json
{"version":1,"rooms":{"J2QWMUJF":{
  "HostKey":"QSXp2kt4WxiZwdySzs0Jgwme5vSs4WF/U/Qe8AP5K2Y=",
  "Card":"ybxAYtu2BUZ4LJCPSRurpfzaMfR+Tqxjd1nOEtbbOB2PBtGTns6GrzyLr1cfZ9113wQja8JYWRnPrLjsBz/It0/yr5olyoGf16BtCHbLyA==",
  "Network":"kanpachi-b8cdca2cd5c34077e3c9aaabddea60a3",
  "PinUntil":"2026-09-03T22:53:54Z","ClosedAt":"0001-01-01T00:00:00Z"}}}
```

The `Network` key is the *rendezvous* network and the Go field behind it is called `Rendezvous`: the
key is frozen so a deployed seed keeps its rooms across the rename.

The room in that dump is called `NOMBRE DE SALA SECRETO` and its host is `Humberto`. Neither string
appears in the file, because the card arrived sealed.

**There are no addresses in that file, and there is no access log.** The only thing the registry does
with a client's IP address is count requests against a fixed window, in memory, evicted as it goes:
thirty a minute in general, five a minute against the hosting password
([`registry/http.go`](registry/http.go)). Nothing writes it down. Every endpoint the whole HTTP
surface has, and what guards each one, is in [`registry/API.md`](registry/API.md).

One caveat: the engine keeps its own console log, at `info` level, on the operator's machine. Any
server operator can, at minimum, see the addresses currently connected to their own server. That is
true of every server on the internet, and it is why *whose* seed you use matters.

## What a hostile seed can do

Everything above describes **the seed whose source is in this repository**. Anyone can run a seed,
and a modified one is still a working seed. Assume that one built to spy could:

- **Log every public IP that introduces itself to it**, with timestamps, and keep the list forever.
- **Keep the graph:** who met whom, how often, for how long, and how much traffic went through it
  while relaying.
- **Keep every room card it was ever handed**, still encrypted, still unreadable to it, but stored.
- **Try to serve a room card the host never wrote, and be caught at it.** The host signs the card
  with its long-term key, and both readers now check that signature against the key the registry
  itself pinned for that code: the app refuses to open a card that does not match, and the
  invitation page says it could not verify the invitation instead of printing the name and nickname
  it was handed. A seed that has been taken over is left with the two moves it cannot be caught at
  from a browser with no memory: serving a different key, or serving no signature at all. Telling *those*
  apart needs somebody who remembers the key from last time, which is the app.
- **Lie about what it is doing.** Nothing you can check from the outside distinguishes a seed that
  discards addresses from one that files them.

What even a hostile seed **cannot** do:

- **Read your room's traffic.** It does not have the network secret, it is never sent one, and a
  relayed packet is encrypted before it ever reaches the seed.
- **Read a room card**, for the same reason: the key was in the fragment, which never left the
  browser.
- **Open a port on your machine.** Your machine decides and applies the firewall, from the profile
  of the game you picked, and nothing arriving from the network can widen it.
- **Stay in the middle of a direct tunnel.** Once the peers are connected directly, there is nothing
  for the seed to be in the middle of.

### The lobby, and what closed there

The lobby, the small throwaway network where a guest asks the host for a credential, derives from
the invite ID, so **anyone holding the code can be in it**, and addresses there are self-assigned.
Until recently that was the whole story, and it was a real hole: messages are sealed to the
recipient's session key, which buys confidentiality against whoever carries the bytes and **not**
authentication of the host, so somebody with the code could answer a credential request before the
real host did, and the victim would join *their* network with the game's ports opened towards it.

That is now shut. **The host signs its answer** with the long-term key of its installation, over a
transcript that binds it to that room's rendezvous network and to the guest's own key for that one
request, so a good answer cannot be replayed from another room or at another guest. The guest
checks it against the key **the registry pinned for that code**, which is the part that matters: the
key arrives by a different road than the answer does. The guest refuses an unsigned answer where a
pinned key exists, rather than accepting it as "unverified". That leniency was the whole attack,
spelled out.

### Key continuity, and the gap it does not close

Every check above is against a key learned from the registry. Kanpachi also remembers, which is the
mechanism SSH and Signal use: your machine keeps a book of the hosts you have joined (the key, the
nickname it used, when you first and last saw it), and the confirmation screen says what it finds.
"You have played with Humberto, in 5 rooms" is a different sentence from "this is the first time",
and a known nickname arriving with a *different* key is a warning, printed with the old fingerprint
above the new one so you can compare the two over any channel you already trust.

**The warning does not lock the door.** Reinstalling Windows generates a new key legitimately, and a
block inside a game is a button people click without reading. Signal started by blocking on a key
change and moved to advising, for the same reason. The button stays and reads "enter anyway".

The gap that is left is the one every system of this kind has, and it is worth stating rather than
hiding: **the first time, there is nothing to compare against.** The book says the key is the same one as before. It never says whose it is.
That is also what Signal's key transparency says of itself: its log attests structural integrity,
and the fallback for identity is still comparing a fingerprint by hand. If a case ever warrants it,
compare the fingerprint with your friend over another channel. Decision 25 in
[`docs/02-decisiones-de-diseno.md`](docs/02-decisiones-de-diseno.md) has the whole reasoning.

One more thing worth stating precisely, because the comparison to Signal invites the wrong
conclusion. Signal's own anonymous envelope (sealed
sender) hides the sender **from the server** and the recipient still authenticates it, by checking
that the identity key which encrypted the envelope matches the sender's certificate. Kanpachi's
lobby envelope is anonymous to the transport **and** to the recipient. That is a weaker property,
and it is the whole of the gap above.

## The practical advice

- **Use a seed run by somebody you would lend your house keys to**, or run your own. That is the
  entire trust decision, and it is why the app asks before it talks to one.
- **The invite code is a ticket, not a secret.** It is meant to be pasted into a chat. Renewing it
  closes the door on everyone who has the old one.
- **Running your own is a one-liner.** See [`seed/install.sh`](seed/install.sh) and
  [`docs/04-flujos-y-configuracion.md`](docs/04-flujos-y-configuracion.md). A seed can also require a
  password to host on it, which is what stops strangers from parking their rooms on your bandwidth.
  Joining a room never asks for that password, on any seed.
