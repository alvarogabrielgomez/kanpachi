# UI

## Principio

Dos estados, cero configuración. La UI muestra el estado del sistema en lenguaje humano y nunca pide decisiones técnicas. Todo lo que el daemon sabe (directo o relay, qué puertos están abiertos, por qué falló algo) se dice en texto plano.

## Pantalla 0: tu nombre

Aparece una sola vez, la primera vez que se abre la app. Implementa la decisión 21.

```
┌──────────────────────────────────────────────┐
│                                              │
│   ¿Cómo te ven tus panas?                    │
│                                              │
│   ┌────────────────────────────┐             │
│   │ Alvaro                     │             │
│   └────────────────────────────┘             │
│   Hasta 12 letras y números                  │
│                                              │
│   Es solo para que se reconozcan en la       │
│   lista. No es una cuenta, no se verifica,   │
│   no se manda a ningún servidor.             │
│                                              │
│              ┌───────────────┐               │
│              │   Continuar   │               │
│              └───────────────┘               │
└──────────────────────────────────────────────┘
```

- **Obligatorio.** Sin nombre no se entra ni se crea una sala. Es lo único que la app pide en toda su vida.
- Se puede cambiar después desde "Avanzado". El cambio aplica en la próxima sala, no en la activa.
- Validación en vivo: se aceptan letras y números, hasta 12. Lo demás no se puede ni escribir, así no hay mensaje de error que leer.
- El texto de abajo es obligatorio y literal. Es la única pantalla del producto que parece un registro, y desactivar esa lectura vale más que ahorrar tres líneas.
- **Sustituye el nombre del equipo.** Sin esto, el motor publicaría a todos los peers el nombre de la máquina en Windows, que suele traer el nombre real de la persona.

## Pantalla A: sin sala

```
┌──────────────────────────────────────────────┐
│  Kanpachi                              v1.0  │
│                                              │
│   Código de sala                             │
│   ┌────────────────────────────┐  ┌────────┐ │
│   │ A7K2-M9QX@servidor         │  │ Unirse │ │
│   └────────────────────────────┘  └────────┘ │
│                                              │
│                    o                         │
│                                              │
│   ┌──────────────────────────────┐           │
│   │         Crear sala           │           │
│   └──────────────────────────────┘           │
│                                              │
│   Tus juegos                                 │
│   ┌──────────────────────────────┐           │
│   │  Project Zomboid             │           │
│   │  Minecraft (Java)            │           │
│   │  Terraria                    │           │
│   ├──────────────────────────────┤           │
│   │  Ver toda la biblioteca (18) │           │
│   └──────────────────────────────┘           │
│                                              │
│  ● Servicio activo                           │
└──────────────────────────────────────────────┘
```

- El campo acepta las seis formas y **no toca lo escrito**: con o sin guiones, mayúsculas o minúsculas, con el servidor pegado (`A7K2M9QX@seed.midominio.com`) o en forma URL (`kanpachi.accentio.dev/A7K2M9QX`, con o sin `https://`, y con el fragmento de la clave detrás). Interpretarlo es de `InviteCode.parse`, que solo decide si se enciende el botón y con qué servidor se pregunta la confianza; validarlo es del daemon, que recibe el texto tal cual.
- **El campo NO enmascara, y esto ya se rompió dos veces por escrito.** Filtraba al alfabeto del código y cortaba a nueve caracteres, así que de las seis formas no entraba ninguna: el `@`, los puntos, las barras y los dos puntos se caían al escribir Y al pegar. Medido pegando `A7K2-M9QX@seed.ejemplo.com`: en el campo quedaba `A7K2-M9QX`. Un código pelado no sirve para entrar desde que el servidor viaja dentro del código, así que **el botón no se encendía nunca**, y no había forma de que se encendiera. El tope del campo es el mismo que mira el daemon antes de tocar el contenido.
- **Un código pelado se explica debajo del campo, mientras se escribe.** Ocho caracteres bien puestos con el botón apagado no dicen qué falta, y lo que falta es la mitad que decide a qué sala se entra: los mismos ocho caracteres son salas distintas en servidores distintos. Es el mismo mensaje que el daemon contesta con `seed_missing`, dicho antes de pulsar en vez de después.
- La pista del campo enseña la forma entera, `A7K2-M9QX@servidor`. Enseñaba solo el código, o sea justo la mitad que no sirve para entrar a ninguna parte.
- **"Crear sala" no pide juego.** Pide un nombre para la sala, y nada más. La sala es independiente del juego activo, decisión 20: nace con red cifrada y cero puertos abiertos, que es un estado válido, y el juego se elige adentro. El nombre es presentación pura, viaja cifrado dentro de la tarjeta y el seed no puede leerlo; se acota a 40 caracteres al escribirlo, no solo al mostrarlo, para que el host vea lo mismo que van a ver los demás.
- **La detección ordena, jamás filtra.** Arriba aparecen los juegos detectados como instalados, que es el atajo del 90% de los casos. Debajo, siempre visible, el acceso a la biblioteca completa del catálogo, con buscador. La detección puede fallar por muchas razones (juego fuera de Steam, instalado en una unidad rara, comprado en Epic o GOG, manifiesto que no se pudo leer) y ninguna de ellas puede impedir crear una sala.
- Si el usuario elige un juego que la detección no encontró, se crea la sala igual, sin advertencias ni fricción. Kanpachi no tiene por qué tener la razón sobre qué hay instalado en la máquina.
- El punto de estado inferior refleja el servicio: verde activo, gris arrancando, rojo con mensaje accionable.

### Por qué volviste a esta pantalla

Si la sesión anterior terminó sola, la pantalla lo dice en una línea, arriba del campo de código. Sin esto, que te expulsen, que el host cierre, que desaparezca veinte minutos y salir por tu cuenta se ven exactamente igual.

| Motivo | Texto |
|---|---|
| Saliste tú | Sin texto. No hay nada que explicar |
| El host te sacó | "El host te sacó de la sala." |
| El host cerró la sala | "El host cerró la sala." |
| El host desapareció veinte minutos | "El host llevaba veinte minutos sin aparecer, así que Kanpachi cerró todo lo que había abierto." |
| El túnel no volvió | "La conexión con la sala no volvió. Kanpachi lo intentó durante diez minutos y cerró todo lo que había abierto. Vuelve a pegar el código cuando tengas red." |
| No se llegó a entrar | "No se pudo entrar a la sala." |

Las dos del medio y las dos de abajo llevan la misma coletilla sobre lo que se cerró, y es a propósito: responde la pregunta que la gente se hace sola, que es si quedó algo abierto.

### Volver a la última sala

Debajo del campo de código, si hubo una sala anterior como invitado:

```
│   Volver a la última sala                    │
│   ┌──────────────────────────────┐           │
│   │  Los panas · A7K2-M9QX       │           │
│   └──────────────────────────────┘           │
```

- Es el mismo ingreso de siempre con el código guardado. No hay un camino de entrada distinto, y por lo tanto no hay una forma distinta de fallar.
- **El código guardado se mantiene vigente cuando el host lo renueva**, porque se lo reparte a los que están dentro en ese mismo acto. Ver decisión 23. Sin eso, esta función caducaría en silencio y el usuario lo descubriría al fallar.
- Lo guardado es el código, el seed, el nombre de la sala y tu nick. **Nunca la credencial**: volver pasa otra vez por la puerta del host, que es lo que hace que revocar siga sirviendo.
- Que te hayan expulsado no borra esta entrada. Expulsar no es banear.

## Pantalla B: en sala

```
┌──────────────────────────────────────────────┐
│  Sala kanpachi.accentio.dev/A7K2M9QX              │
│                                   [Copiar enlace] │
│                                              │
│  Project Zomboid   (host: Humberto)          │
│  Conéctate a 100.87.3.1 : 16261    [Copiar]  │
│                                              │
│  Abierto solo dentro de Kanpachi:            │
│  16261-16262 UDP, visible para 4 personas    │
│  Tu router sigue cerrado. Internet no ve nada│
│                                              │
│  Solo te conectas con el host. Los demás     │
│  jugadores no alcanzan tu PC.                │
│                                              │
│  En la sala                                  │
│  ● Humberto (host) 100.87.3.1  directo  28ms │
│  ● Gabriel       100.87.3.2   directo   45ms │
│  ◐ Santiago      100.87.3.3   relay    140ms │
│  ● Alvaro (tú)   100.87.3.4                  │
│                                              │
│  ┌──────────────────────┐  [Copiar reporte]  │
│  │   Salir de la sala   │                    │
│  └──────────────────────┘                    │
└──────────────────────────────────────────────┘
```

**«Copiar enlace» copia el enlace de verdad**, con el seed de esta sala en el host y la clave de la tarjeta en el fragmento. Pegaba un literal con `kanpachi.accentio.dev` escrito dentro y nada después del código, y eso se llevaba dos cosas por delante: quien se autohospeda repartía enlaces al registro de otro, y la página nunca podía descifrar la tarjeta, de modo que toda invitación se leía «una sala de Kanpachi» en vez del nombre de la sala y de quién la mandó.

El enlace viene armado del daemon y **no se compone en la pantalla**. No es preferencia: la clave de la tarjeta no viaja en ningún otro campo del estado, así que un enlace compuesto acá solo puede salir sin ella. Cuando el daemon no lo manda, el botón no se dibuja: pegar una forma a medias es peor que no ofrecer el botón.

- Verde: conexión directa. Ámbar: vía relay, con tooltip "Funciona con más latencia, el NAT de una de las puntas no permitió conexión directa".
- **La topología se dice en texto, siempre.** Sale del perfil del juego, de si `client_ports` está vacío. Con `client_ports` vacío: "Solo te conectas con el host. Los demás jugadores no alcanzan tu PC". Con `client_ports` no vacío: "Este juego conecta a todos con todos. Se abren los puertos del juego hacia los demás miembros". Es la aplicación directa del principio de que la seguridad que no se ve no genera confianza, y es la diferencia que el jugador tiene derecho a conocer antes de entrar.

### Expulsar, solo en la vista del host

Cada miembro de la lista lleva un botón de expulsar, visible **únicamente si tú eres el host**. Implementa la decisión 22.

```
│  ◐ Santiago      100.87.3.3   relay    140ms  [Expulsar] │
```

Al pulsarlo, confirmación de una línea que dice la verdad completa y no promete de más:

```
┌──────────────────────────────────────────────┐
│  Expulsar a Santiago                         │
│                                              │
│  Sale de la sala ahora mismo.                │
│                                              │
│  Puede volver a entrar si todavía tiene el   │
│  código. Para que no vuelva, renueva el      │
│  código: los que ya están dentro se quedan.  │
│                                              │
│   [Cancelar]  [Expulsar]  [Expulsar y        │
│                            renovar el código]│
└──────────────────────────────────────────────┘
```

- **El tercer botón existe porque renovar es el único control que cierra la puerta.** Sin él, el usuario que de verdad no quiere que alguien vuelva tiene que ir a buscarlo a otra parte de la pantalla sin que nada le diga que le hace falta.
- El invitado no ve el botón, ni en su fila ni en las ajenas.
- **Al expulsado sí se le avisa**, y el aviso sale ANTES de cortarle nada, que es el único orden en que puede llegar. Su app dice "el host te sacó de la sala" y cierra limpio. Es cortesía, no es lo que expulsa: un cliente modificado que lo ignore sale igual y en el mismo segundo. Ver decisión 22.
- Los nombres no son únicos. Si hay dos "Santiago", la fila muestra también la IP virtual, que sí lo es.

#### Cuando la expulsión se aplica a medias

Las dos capas corren siempre y ninguna aborta a la otra, así que puede fallar una y funcionar la otra. Eso se dice, no se esconde, y el texto cambia según cuál falló:

| Qué falló | Texto |
|---|---|
| El motor no le cerró la sesión | "Saqué a Santiago de tus reglas: ya no alcanza ningún puerto tuyo. El motor no le cerró la sesión, así que sigue viendo la red. Renueva el código para que no vuelva." |
| Las reglas no se recalcularon | "El motor le cerró la sesión a Santiago. Tus reglas no se recalcularon: vuelve a intentarlo, o vuelve a elegir el juego." |
| Las dos | "No se pudo expulsar a Santiago. Revisa el diagnóstico y renueva el código." |

El aviso se queda en pantalla hasta que las reglas se apliquen bien. Es una de las alertas PEGAJOSAS, que sobreviven al refresco del módulo de exposición porque describen algo que pasó y que nadie va a volver a medir. Acá se leía «una de las dos» y era un número que envejeció solo: cuántas son se decide en `AlertKind.Sticky`, y contarlas en prosa es una copia que se desincroniza.

### Renovar el código

Botón junto al código, visible solo para el host. Es el control que cierra la puerta, separado del que saca a alguien:

```
┌──────────────────────────────────────────────┐
│  Renovar el código de la sala                │
│                                              │
│  El código actual deja de funcionar.         │
│  Los 3 que están dentro siguen dentro.       │
│  Pásales el nuevo solo a quien quieras que   │
│  pueda volver a entrar.                      │
│                                              │
│      [Cancelar]      [Renovar]               │
└──────────────────────────────────────────────┘
```

Las dos perillas son independientes y la UI lo dice con esas palabras, porque la diferencia no es obvia: **expulsar** saca a alguien que está dentro, **renovar** impide entrar a quien está fuera. Ninguna hace el trabajo de la otra.

**Mientras corre, el botón gira y se apaga**: dice «Renovando…» con una rueda en el sitio del icono. No es cosmético. Renovar es la única operación de la sala que depende de internet, porque habla con el registro del seed, y su plazo son treinta segundos; sin nada que lo diga, el botón parece muerto y se vuelve a pulsar, que son dos rotaciones seguidas y la segunda mata el código que la primera acaba de repartir. La rueda ocupa el sitio del icono y no el del texto para que el botón no cambie de ancho al pulsarlo, y con él la fila entera.

Apagarlo es la mitad que importa: una rueda girando sobre un botón que se sigue pudiendo pulsar invita exactamente a lo que hay que impedir. Es el mismo argumento por el que la sala se pone en gris mientras se aplica un juego, llevado al tamaño de un botón, porque lo que tarda un segundo no merece apagar una pantalla entera.

#### Cuando el registro perdió el código

La sala real puede seguir funcionando para quienes ya están dentro aunque el registro se haya reiniciado o haya olvidado su entrada. El host ve el aviso en la sala; un invitado no, porque no puede resolverlo:

```
┌──────────────────────────────────────────────┐
│  El código de esta sala dejó de funcionar    │
│                                              │
│  La sala sigue funcionando para quienes ya  │
│  están dentro, pero nadie nuevo puede entrar │
│  con ese código. Renuévalo para abrir una    │
│  puerta nueva sin cortar la partida.         │
│                                              │
│                 [Renovar el código]          │
└──────────────────────────────────────────────┘
```

El botón renueva solo el código y conserva la red real, el juego y a los miembros presentes. No crea otra sala ni rota nada en silencio: todos los enlaces anteriores dejan de servir únicamente después de esa acción explícita.

### Cuando el host se va

Implementa la decisión 20. La conexión sigue bien, lo que falta es la persona que corre el juego, así que no se muestra como error de red:

```
┌──────────────────────────────────────────────┐
│  ⏸  Humberto salió de la sala.               │
│     El juego corría en su PC, así que no hay │
│     a qué conectarse hasta que vuelva.       │
│                                              │
│     Nadie tiene puertos abiertos ahora.      │
│                                              │
│     [Salir de la sala]                       │
└──────────────────────────────────────────────┘
```

- La segunda línea es obligatoria. Es la que responde la pregunta que la gente se hace sola, que es si quedaron expuestos.
- Si el host vuelve, el aviso desaparece solo y la guía de conexión reaparece. No hay que hacer nada.
- **A los veinte minutos, si no volvió, Kanpachi sale solo.** Se cierran los puertos, se revierten los ajustes y se vuelve a la pantalla A diciendo por qué. Cada máquina lo decide por su cuenta, sin coordinarse con nadie: ver decisión 20.
- Nadie hereda el rol. La UI no ofrece "hospedar tú", porque eso es crear una sala nueva.
- El bloque de exposición es obligatorio y literal, y siempre lleva las dos líneas. La primera dice qué se abrió y para quién, la segunda aclara que nada de eso toca el router. Esa segunda línea es el argumento central del producto puesto donde la gente lo lee. Sin juego activo dice: "Nada abierto. La red está en cuarentena. Tu router sigue cerrado".
- Nunca decir "puerto abierto" a secas. Son dos cosas distintas y confundirlas es exactamente el miedo que originó el producto: **puerto en el router** lo alcanza todo internet y Kanpachi jamás lo toca, **puerto en la interfaz virtual** solo lo alcanzan los miembros de la sala.

### La pantalla de exposición, y cómo se llega

El bloque de la sala dice lo que Kanpachi **pidió** abrir. La pantalla de
exposición dice lo que el sistema **tiene**, medido. La diferencia entre las dos
es lo que esta pantalla existe para enseñar: un puerto pedido que no está puesto
significa que alguien no va a poder entrar, y sin medirlo no se ve hasta que un
amigo se queda fuera.

Se llega desde el bloque de exposición de la sala, con un enlace debajo:
**"Ver lo que tu PC tiene abierto"**. Va en las DOS caras del bloque, incluida la
de "nada abierto", y eso es deliberado: "nada abierto" es justo la afirmación
que más falta hace poder desmentir.

Y se vuelve con la flecha del encabezado. Sin la vuelta la pantalla es una
trampa: el usuario entra a mirar sus puertos y se queda sin su sala.

Arriba del todo va la banda de la Protección Kanpachi, **encima del encabezado**,
porque es lo único de esa pantalla que puede desmentir todo lo de abajo. La lista
mide lo que esta PC tiene configurado; la alarma dice que un paquete cruzó igual.
Debajo se leería después de haber creído la lista.

Lo que esta pantalla NO hace: cuando la medición falla, no enseña la última lista
buena. Dice que Kanpachi no pudo leer lo que tiene puesto y deja la lista fuera.
Misma doctrina que el aviso de auditoría caída, y por la misma razón: una lista
vieja pintada de verde es peor que una pantalla que admite no saber.

### Probar desde otra PC

Debajo de la lista de exposición, y debajo a propósito: arriba está lo que esta
PC tiene configurado, y esto es lo que otra máquina alcanza de verdad. Leerlo en
ese orden es leer primero la promesa y después la comprobación.

Tiene dos caras y no un botón que a veces no anda.

**En un invitado**, un botón que marca a la PC del host y cuenta qué contestó:

```
┌──────────────────────────────────────────────┐
│ LO QUE SE ALCANZA DESDE AQUÍ                 │
│ Probado a las 20:14:03    [Probar la PC de…] │
│                                              │
│ ✓ Desde acá no se alcanza nada más de esa PC │
│   Contestó el canal de la sala, así que la   │
│   comprobación llegó de verdad, y ninguno de │
│   los puertos peligrosos contestó.           │
│   Se prueban puertos TCP conocidos, no todos │
│                                              │
│ 445 · compartir archivos (SMB)               │
│ No tiene que contestar        sin respuesta  │
│ 57623 · el canal de la sala                  │
│ Tiene que contestar          contesta · 11ms │
└──────────────────────────────────────────────┘
```

**En el host**, la frase que necesita y ningún botón: *"esto lo tiene que pulsar
alguien más de la sala"*, con el porqué. Su PC no se puede comprobar a sí misma,
porque lo que se manda a la propia dirección no pasa por el firewall.

Las reglas de escritura de este bloque, que son lo que lo hace útil:

- **Una fila callada dice "sin respuesta", jamás "cerrado".** Está medido que en
  Windows el silencio no distingue "bloqueado" de "no hay nada escuchando", así
  que escribir "cerrado" ahí sería afirmar lo que la medición no dice.
- **Cada fila dice por qué está ese puerto en la lista.** Sin eso, el canal de la
  sala contestando se lee igual que SMB contestando, y son lo contrario.
- **"No se pudo alcanzar" no es "cerrado", y se pinta distinto.** Si ni el canal
  contesta, lo que hay es una comprobación que no llegó, y se dice así.
- **El resumen limpio lleva su advertencia de alcance.** Sin ella, "no se alcanza
  nada" se lee como "no hay nada abierto", y es falso: se prueban unos cuantos
  puertos TCP conocidos, y por UDP no se puede preguntar.
- **Una fuga se nombra con el puerto que contestó.** Decir "hay algo abierto" sin
  decir qué manda al usuario a buscar a ciegas.
- Un fallo borra el resultado anterior. Un resultado viejo al lado de un error
  nuevo se lee como si siguiera valiendo.

### La Protección Kanpachi, y el aviso de que no está puesta

Es el nombre del concepto de cara al usuario: **la Protección Kanpachi** es que
todo lo que no pidió el juego está cerrado en el adaptador virtual. No se explica
como "un filtro WFP" ni como "el deny-all": se explica como una cosa que está
puesta o no lo está.

El canario la comprueba desde otra máquina, sola, sin que nadie pulse nada. Ver
`03-arquitectura.md`. Cuando funciona, **no se ve nada**: es el producto haciendo
su trabajo.

**La primera fuga NO produce aviso.** El daemon la repara solo, en silencio, y
deja que la ronda siguiente juzgue. Solo la segunda ronda con fuga seguida
levanta la alarma. Eso cambia lo que el aviso significa: deja de decir "pasó algo,
pulsa el botón" y pasa a decir **"pasó algo, lo intenté arreglar solo, y no
aguantó"**.

Lo que se gana es que **la reparación deja de depender de que el usuario haga
caso**. Un usuario que ignore el aviso para siempre igual tiene la protección
repuesta. Ver decisión 28.

Cuando la alarma sí salta, lo que dice **no habla de un puerto**. Palabra por
palabra, igual que `ui/lib/core/messages/message_catalog.dart`:

```
┌──────────────────────────────────────────────┐
│ ⚠  Tu protección no está conteniendo         │
│                                              │
│    Alguien de la sala alcanzó un puerto de   │
│    esta PC que tenía que estar cerrado.      │
│    Kanpachi ya intentó reponer la protección │
│    y no aguantó.                             │
│                                              │
│    Vuelve a aplicarla. Si el problema sigue, │
│    sal de la sala: eso cierra todo lo que    │
│    Kanpachi abrió.                           │
│                                              │
│    Comprobado a las 22:15:03 desde las PCs   │
│    de 3 personas de la sala.                 │
│                                              │
│              [Volver a aplicar la protección]│
└──────────────────────────────────────────────┘
```

La última línea es el detalle, y lo pone la pantalla y no el catálogo: el copy es
del producto y el dato es del daemon.

Las reglas de escritura de este aviso:

- **No se nombra el puerto.** El canario vive en un puerto al azar que Kanpachi
  abrió hace dos segundos y ya cerró, y ese puerto no le importa a nadie. Lo que
  falló es la contención entera, no un hueco. Decir "tienes el puerto 51023
  abierto" sería tres veces falso y mandaría al usuario a buscar algo que no
  existe.
- **Se dice quién lo comprobó.** Es lo que hace la frase creíble, y de paso
  explica por qué el aviso aparece ahora y no antes. Con un solo preguntado se le
  nombra; con varios va el número, porque cuatro nicks seguidos en una banda de
  aviso se leen como ruido.
- **Se dice que Kanpachi ya lo intentó.** No es cortesía: es lo que hace que el
  usuario entienda que la protección ya se repuso una vez sin él, y por lo tanto
  que esto es la segunda vez. Sin esa frase, el aviso se lee como el primer
  síntoma cuando en realidad es el segundo.
- **El botón repara, no cierra.** Es reaplicar el conjunto entero, que ya es
  idempotente: pulsarlo con todo bien no hace nada, y pulsarlo con la compuerta
  rota la repone. Se puede pulsar siempre y sin miedo, que es lo que lo hace
  útil sin tener que creerle a nadie.
- **Se avisa del efecto secundario, antes de pulsar.** Reponer la protección
  puede cortar programas ajenos que estaban funcionando por la red virtual. Se
  dice con esas palabras, y se dice también que vuelven al salir de la sala o al
  cerrar Kanpachi. Es exactamente lo que el producto promete hacer, y aun así el
  usuario tiene derecho a saberlo.
- **El silencio NO se celebra.** No hay un "todo comprobado, estás a salvo" en
  verde. Una ronda callada significa que nadie encontró evidencia de fuga, y eso
  también pasa si nadie llegó a marcar. Como mucho, una línea gris: *"comprobado
  a las 20:14 desde la PC de Humberto"*.

### Aviso de exposición ajena

Aparece bajo el bloque de exposición cuando la auditoría encuentra reglas del propio juego que lo dejan alcanzable por fuera de Kanpachi:

```
┌──────────────────────────────────────────────┐
│ ⚠  Project Zomboid dejó una regla en tu      │
│    firewall                                  │
│                                              │
│    La puso su instalador, y deja el juego    │
│    alcanzable desde tu red de casa y desde   │
│    cualquier otra a la que conectes este PC, │
│    con Kanpachi cerrado. Dentro de la sala   │
│    no cambia nada: ahí manda Kanpachi.       │
│                                              │
│    [Desactivar mientras juego]  [Dejar así]  │
└──────────────────────────────────────────────┘
```

Al elegir desactivar, la línea pasa a "Regla desactivada. Se restaura al salir de la sala". Nunca se actúa sin ese click. Las reglas se desactivan, jamás se borran. Mientras se escribe, el botón dice "Desactivando…" y no se deja pulsar: escribir en el almacén de reglas de Windows por COM tarda alrededor de un segundo, y sin nada que lo diga lo que hace la gente es pulsarlo otra vez.

#### El texto DECÍA de más, y se corrigió

Decía que la regla dejaba el juego alcanzable "por toda la sala, fuera del control de Kanpachi", con "expulsar a alguien no lo tapa" debajo. **Eso es justo lo que la compuerta existe para que sea falso.** La compuerta es un bloqueo duro de WFP acotado al adaptador virtual, y en WFP un Block gana sobre cualquier permiso ajeno sin desempate por especificidad: dentro de la sala esta regla no consigue nada, y a un expulsado lo sigue tapando la compuerta. La frase venía de la decisión 12, que es anterior a la 27, y se quedó sin actualizar cuando la compuerta pasó a existir.

Lo que sí queda al descubierto es todo lo demás, y es real: la compuerta está acotada al adaptador virtual **a propósito**, porque esa acotación es lo que impide dejar al usuario sin la entrada de su red de casa. Ahí esta regla vale, sigue puesta con Kanpachi cerrado, y la dejó el instalador del juego para siempre.

Se corrige porque un aviso que exagera no protege más: enseña a no leer los avisos.

**Esto NO es la Protección Kanpachi ni el canario, y se confunden fácil.** Son tres cosas distintas: la Protección son las dos capas de contención que Kanpachi escribe; el canario es cómo se comprueba desde otra máquina que esas capas están puestas; y esto es una regla que Kanpachi **no** escribió, encontrada consultando el almacén de reglas de Windows por ruta de ejecutable. No hace falta que haya nadie en la sala para verla, porque no se mide nada de la red: la regla está en disco haya o no partida. Por eso aparece cada vez que se activa un juego, que es cuando se pregunta por el ejecutable de ese juego.

#### Son DOS avisos, no uno

La auditoría clasifica lo que encuentra y el aviso cambia entero según la clase. Tratarlas igual era el bug: una regla de más para el juego molesta, una de escritorio remoto entrega la máquina.

```
┌──────────────────────────────────────────────┐
│ ⚠  Un programa de control remoto está        │
│    abierto en tu firewall                    │
│                                              │
│    Quien entre a la sala puede llegar a él   │
│    y quedarse con tu teclado, tu pantalla y  │
│    tus archivos, aunque lo expulses después: │
│    el código de invitación no es un secreto. │
│    Hay que resolverlo antes de abrir la      │
│    sala.                                     │
│                                              │
│    C:\Program Files\Parsec\parsecd.exe       │
│                                              │
│    [Desactivarlo mientras juego]             │
└──────────────────────────────────────────────┘
```

**No lleva "Dejar así", y esa ausencia es la decisión.** En la del juego, dejarla es una elección legítima del usuario sobre su propia máquina. Acá dejarla abre la sala con el escritorio del host alcanzable por cualquiera que tenga el código, y el código no es un secreto ni existe el baneo. La única salida sin desactivar nada es no abrir la sala.

El texto nombra **teclado, pantalla y archivos** en vez de decir "riesgo de seguridad", y hay un test que lo exige. La frase genérica se despacha con un click; la concreta obliga a pesar la decisión, que es justo lo que un aviso bloqueante tiene que ganarse.

La ruta del ejecutable va como detalle bajo el cuerpo, jamás dentro de él: el texto del producto lo escribe el catálogo y el dato concreto lo aporta el daemon.

**Una clase que esta versión no conozca se pinta como control remoto**, que es el aviso más severo. Viene de un daemon más nuevo que aprendió a detectar algo que la UI no sabe nombrar, y de las dos formas de equivocarse, sobreavisar molesta mientras que esconderlo rompe la promesa.

- La guía de conexión cambia por perfil: `direct_ip` muestra IP y puerto con botón de copiar, `lan_discovery` muestra "La partida aparece sola en el menú LAN del juego".

**La tercera es distinta de las otras dos y el texto tiene que dejarlo claro.** Las demás dicen que encontraron algo; esta dice que no pudo mirar. Sin ese aviso, una auditoría caída y una máquina impecable se ven idénticas desde acá: las dos pintan verde. Aparece cuando falla cualquiera de los dos chequeos locales, y se va sola cuando vuelven a contestar. La consulta al router no la levanta, porque la mayoría de los routers nunca contestan y el aviso quedaría encendido para siempre.

Reglas:

- **Nunca bloquean.** Se puede crear y unirse a salas con alertas vigentes. Informan, no impiden. Un falso positivo que deje a alguien sin jugar contradice el principio de que la detección ordena y jamás filtra.
- **Kanpachi no arregla nada por su cuenta.** No enciende el firewall del usuario, no cierra puertos del router. Explica y enlaza a cómo hacerlo. Tocar la configuración global de la máquina sin pedirlo es lo que hace el software que este producto no quiere ser.
- Cada alerta sigue la regla de microcopy: qué pasa, qué significa, qué hacer.
- Desaparecen solas cuando la condición deja de existir. No hay que descartarlas a mano.

**La que habla de puertos que NO están abiertos.** Todas las de arriba avisan de exposición de más, y hay una que avisa de lo contrario:

```
┌──────────────────────────────────────────────┐
│ ⚠  La sala volvió sin su juego               │
│    La sala está abierta y con el mismo       │
│    código de siempre. Lo que no se pudo      │
│    reponer es el juego que tenía activo,     │
│    así que no hay ningún puerto abierto y    │
│    quien entre no va a poder jugar.          │
│    Vuelve a elegir el juego.                 │
└──────────────────────────────────────────────┘
```

Aparece cuando el daemon reabre solo la sala del arranque anterior y el perfil que estaba activo ya no está en el catálogo de esa máquina, o sus reglas no se pudieron reponer. **El texto empieza diciendo que la sala está bien**, y esa primera frase es la que hace falta: sin ella el título se lee como una avería de la sala, cuando lo que pasa es que la sala funciona y el juego no está puesto.

Está en esta franja aunque no sea un hallazgo de exposición, porque comparte lo único que define a una alerta acá: anula la promesa del producto si nadie la mira. El caso que la motiva es un servidor de juego en una máquina que nadie mira, donde el síntoma sin este aviso es que la gente entra a la sala y el juego no responde. Es pegajosa, y la apaga elegir un juego.

## Pantalla C: confirmación de apertura externa

Cuando la app se abre desde un enlace `kanpachi://`, sea desde Telegram o desde la página de invitación, **nunca entra sola a la sala**. Abre así:

```
┌──────────────────────────────────────────────┐
│                                              │
│   Te invitaron a una sala de Kanpachi        │
│                                              │
│   Sala       A7K2-M9QX                       │
│   Servidor   kanpachi.accentio.dev           │
│   Host       Humberto  ab3f-9k2m             │
│              ✓ ya jugaste con él, 3 salas    │
│                                              │
│   Al entrar, tu equipo se conecta con los    │
│   demás miembros de esta sala. Nada de tu    │
│   PC queda expuesto hasta que se elija un    │
│   juego.                                     │
│                                              │
│   ┌──────────────┐   ┌───────────────────┐   │
│   │   Cancelar   │   │  Entrar a la sala │   │
│   └──────────────┘   └───────────────────┘   │
└──────────────────────────────────────────────┘
```

**Acá es donde la decisión 25 vale de verdad.** La página web muestra el nick sin poder juzgarlo, porque el navegador no recuerda con quién jugaste. Esta pantalla sí tiene la libreta, así que es la única que puede pronunciarse.

| Lo que dice la libreta | Lo que muestra el bloque |
|---|---|
| Misma llave, mismo nick | «Ya jugaste con Humberto, en 5 salas. Es la misma llave de siempre», con la huella debajo |
| Llave nueva | «Es la primera vez que entras a una sala de Humberto. No hay con qué comparar todavía», con la huella. Sin alarma: es el estado normal de toda primera invitación |
| Misma llave, otro nick | «Es la llave de Humberto, con la que ya jugaste. Ahora se identifica como Beto» |
| **Nick conocido, OTRA llave** | **«Ojo: Humberto te invitó antes con otra llave»**, con el borde en rojo y las dos huellas una encima de la otra, `ANTES` y `AHORA`, y el botón pasa a decir «Entrar igual» pintado como el de cancelar |
| Sin llave fijada | El bloque no aparece. Sin llave que recordar no hay continuidad de la que hablar, y una huella sin nada detrás decora |

El aviso no bloquea. Cambiar de máquina o reinstalar Windows produce una huella nueva legítimamente, y bloquear convertiría un caso común en soporte —es el camino que hizo Signal, que empezó bloqueando y se movió a avisar—. Lo que hace es invertir el peso visual, o sea que entrar deja de ser el camino cómodo.

**El bloque aparece en los DOS sitios donde se confirma**, con el mismo widget: la pantalla de un enlace que llegó de fuera, y el diálogo de confianza al pegar un código. Para el segundo la ventana resuelve el código contra su registro antes de abrir el diálogo, para que la huella esté ahí cuando aparece y no un instante después, con el botón ya pulsable.

Reglas:

- **Siempre aparece.** No hay "recordar esta sala" ni "no volver a preguntar". El estado recordado de confianza se eliminó del diseño precisamente para que no exista forma de saltarse esta pantalla.
- **El diálogo del navegador no la reemplaza.** Chrome y Edge preguntan si abrir Kanpachi, sin decir a qué sala ni a qué servidor, y ofrecen recordar la elección. Esta pantalla es la que muestra los datos concretos.
- **El servidor se muestra siempre, y ya no hay «el por defecto» contra «uno ajeno».** Esa distinción murió con el seed compilado: hoy todo servidor es el de alguien. Lo que se enseña en su lugar es el bloque de confianza, que es el MISMO widget que usan los dos diálogos de abajo, con la explicación plegable de qué es un servidor y el aviso, desplegado, de lo que puede hacer uno malicioso. Escribirlo tres veces sería cómo una de las tres acaba diciendo algo distinto.
- **La huella se muestra aunque sea conocida.** Verla siempre es lo que hace que verla cambiar signifique algo.
- Cancelar deja la app en la pantalla A, sin haber tocado nada.

### Lo que está construido hoy, y en qué se aparta

La pantalla existía con **datos de relleno**: un código y un nombre de sala escritos a mano en el `switch` que la construye, y el servidor fijo en `kanpachi.accentio.dev`. Ya no. El daemon resuelve el enlace y manda el código, el seed, el nombre de la sala y el apodo del host; por dónde viaja está en `03-arquitectura.md`.

Lo que se aparta del dibujo de arriba, con su motivo:

- **La huella y la libreta SÍ están, y solo cuando hay algo comprobado que decir.** Si la firma de la tarjeta verificó contra la llave que el registro fijó, debajo del servidor aparece un bloque con la huella y con lo que la libreta sabe: «es la primera vez», «ya jugaste con Humberto, en 5 salas», «es la llave de Humberto, ahora se identifica como Beto», o el aviso de huella cambiada con la de antes encima de la de ahora. Sin firma verificada no se pinta nada: una huella que no respalda a nadie decora, y enseñarla enseña a ignorarla. Ver decisión 25.
- **El encabezado dice «Se identifica como Humberto»**, la misma frase que usa la página, y jamás «Humberto te invitó». El apodo no está verificado, así que la pantalla no puede afirmar quién es.
- **Sin tarjeta, la sala se llama «Sin nombre todavía».** Pasa con un código dictado por teléfono, con un enlace sin fragmento, o con el registro caído. No se inventa un nombre.
- **Dos casos quitan el botón de entrar**, y dejan solo «Cerrar»: que el enlace no se entienda, y que el registro **afirme** que esa sala no existe. Que el registro no conteste no cuenta, y el botón se queda. Esta pantalla es una medición de un instante y el registro puede estar de vuelta cuando la persona pulse; quitar el botón por un fallo de hace un momento sería tratar el silencio como una respuesta. Si sigue caído, entrar lo dice en el primer segundo con el mensaje de `no_registry`, y el aviso de la portada ya lo venía anunciando.
- **Un enlace que no se entiende SÍ llega acá**, al revés de lo que decía la línea de abajo. Se enseña tal cual llegó, en su propia fila. Alguien pulsó un botón en su navegador: abrir en la portada como si no hubiera pasado nada lo deja buscando qué falló, y ver el enlace entero es lo que permite notar que venía cortado.
- **Entrar no navega a la sala.** La pantalla de sala aparece cuando el daemon dice que hay sala, y quien lo vigila es el latido. Ir antes enseñaría una sala vacía durante el minuto que tarda en abrirse, y una que no llegó a abrirse dejaría la pantalla puesta sobre nada.
- **El bloque de confianza no aparece cuando el registro AFIRMA que la sala no existe.** No hay decisión que tomar sobre un servidor si no hay sala a la que entrar, y pedir confianza para nada enseña a darla sin leer.

## Pantalla D: en qué servidor abres tus salas

Se llega desde tres sitios: **Configuración**, el diálogo de confianza al abrir, y el fallo de abrir una sala sin servidor configurado. **No aparece al instalar**, y esa es la decisión: quien solo entra a salas de otros no configura nada en toda su vida.

**Los tres, y no solo los dos últimos.** Con los dos de antes, a esta pantalla solo se llegaba FALLANDO, y Configuración —que se presenta como «lo poco que hay que decidir»— no enseñaba el servidor ni dejaba cambiarlo, mientras la barra de estado de esa misma ventana decía «sin servidor». Quien quería mirar en cuál está, o moverse a otro sin esperar a que algo se rompiera, no tenía por dónde. La tarjeta de Configuración enseña el nombre en monoespaciada, por lo mismo que el diálogo de confianza, y lleva acá.

```
┌──────────────────────────────────────────────┐
│      ¿En qué servidor abres tus salas?       │
│                                              │
│        ┌──────────────────────────┐          │
│        │  kanpachi.ejemplo.com    │          │
│        └──────────────────────────┘          │
│   Este es el servidor de la última sala en   │
│   la que estuviste. Cámbialo si no es tuyo.  │
│                                              │
│   Presenta entre sí a los que entran con tu  │
│   código, hasta que la sala se levanta.      │
│   Desde ahí el juego va directo entre        │
│   ustedes. Ponlo solo si confías en quien lo │
│   administra.  Más información               │
│                 ┌──────────┐                 │
│                 │  Guardar │                 │
│                 └──────────┘                 │
└──────────────────────────────────────────────┘
```

- **Se prellena con el servidor de la última sala a la que se entró**, marcado como sugerencia y jamás aplicado solo. Ver la decisión 16: adoptarlo en silencio haría que la siguiente sala se hospede en el servidor de un desconocido.
- **El nombre lo valida el daemon**, con la misma comprobación que aplica al servidor de un código pegado. La pantalla solo exige que haya algo escrito: repetir las reglas de un nombre de dominio en Dart daría dos sitios donde arreglarlas.
- **Guardar PREGUNTA al servidor antes de guardarlo**, y el botón enseña su rueda mientras tanto. Un nombre bien escrito de una máquina que no existe se guardaba igual, y el fallo aparecía en el siguiente intento de abrir una sala, con el nombre ya fuera de la pantalla. El precio se dice entero: configurar el servidor exige conexión, y con el servidor caído no se puede dejar puesto. Es el intercambio que se quiere, porque un servidor que no contesta tampoco sirve para lo que se está guardando.
- El error del daemon se enseña **pegado al campo y con el borde en rojo**, no como aviso de la portada: es de lo que esa persona acaba de escribir. El color solo refuerza, la frase siempre está.
- **El explicador dice qué HACE esa máquina, no qué hace la app con ella.** Decía «es el punto de encuentro de tus salas: ve tu IP pública y por él pasa todo el que entre con tu código», y esa última mitad describe el vestíbulo como si fuera la partida: levantado el túnel el seed se retira, y lo que sigue pasando por él es la conexión que no consiguió camino directo, cifrada. Lo que ve de ti se cuenta entero en el diálogo de confianza, que es donde se decide.
- **Termina en «Más información», que abre `kanpachi-seed.md`.** Es el mismo destino de los otros dos sitios que hablan de un seed, y hasta ahora los dos apuntaban a `Brand.docs` con un ancla `#seed` que no existía en ninguna página: el enlace abría el README y quien lo pulsaba se quedaba con la misma duda. El enlace se SUBRAYA al pasarle el ratón por encima y no siempre: dentro de un párrafo, un subrayado permanente lo parte en dos antes de que nadie quiera pulsarlo, y el color de acento solo no puede significar «pulsable» porque también lo llevan textos que no lo son.
- **Guardar CONTINÚA el flujo que llevó hasta acá.** Viniendo de intentar abrir una sala, se vuelve al diálogo de confianza con el servidor recién puesto, que es donde el flujo se había interrumpido. Antes se volvía a la portada y la sala se quedaba sin abrir, así que había que pulsar «Crear» otra vez y saber que había que hacerlo. La flecha de volver es lo que ABANDONA: quien vuelve atrás decidió no abrirla.

## Pantalla E: la contraseña de un servidor que la pide

Aparece **cuando abrir una sala falla porque el servidor la pide**, y en ningún otro momento. Casi ninguno la pide, así que preguntarla por si acaso le cobraría a todo el mundo el roce de un caso raro.

El mismo momento cubre los tres casos, porque lo que hay que hacer es idéntico y porque el servidor se niega a decir cuál fue: nunca se puso ninguna, la que había caducó, o quien lo administra la cambió.

- El campo va **enmascarado**. La ventana se comparte por pantalla, y quien escribe una contraseña delante de otros tiene que poder hacerlo sin pensarlo.
- **La contraseña no se guarda en ningún sitio de la interfaz.** Vive en el controlador del campo y muere con la pantalla. Lo que sobrevive lo guarda el daemon, sellado, y no vuelve por el cable.
- El texto dice para qué sirve **sin prometer de más**: es de quien administra ese servidor, y sirve para abrir salas en él. **Entrar a una sala nunca la pide.**
- **Se llega en silencio, sin el aviso rojo.** El fallo que trae acá es el único de la lista que se arregla escribiendo algo, y contarlo además como aviso sería decir «ese servidor pide contraseña» flotando encima de la pantalla que la está pidiendo. Vale para las dos pantallas que un fallo abre, esta y la D.
- **Una contraseña rechazada vuelve a esta misma pantalla**, con el motivo debajo del campo y el borde en rojo. No dice si es incorrecta o si caducó: el servidor se niega a decirlo, distinguirlas solo le regalaría información a quien esté probando, y lo que hay que hacer es lo mismo en los dos casos.
- **Aceptarla CONTINÚA con la sala**, sin volver a preguntar la confianza: se llegó acá en mitad de una creación que ya pasó por ese diálogo, y con el token guardado no falta nada más. Antes se volvía atrás y había que pulsar «Crear» otra vez. Sin creación pendiente se vuelve por donde se vino, que es lo correcto para las otras dos puertas: renovar el código y reabrir la sala.

## Los dos diálogos de confianza

Mismo fondo, dos momentos, un solo widget compartido con la pantalla C. Enseñan la dirección del servidor en monoespaciada sobre fondo hundido, que es lo que alguien COMPARA carácter a carácter contra lo que le mandó su amigo.

| | Al abrir | Al entrar |
|---|---|---|
| Encabezado | «Crear una sala» | «Entrar a una sala» |
| De dónde sale la dirección | Lo configurado en esta máquina | El código que pegaron |
| Además | El nombre de la sala, editable ahí mismo | — |
| Botón | «Confiar y crear» | «Confiar y entrar» |

- **La explicación de qué es un servidor va plegada; el aviso de lo que puede hacer uno malicioso, no.** Qué es lo pregunta una vez quien nunca lo oyó; lo que puede hacerte uno malo hay que verlo sin abrir nada, porque es de lo que depende el botón de abajo.
- **Los dos textos dicen lo que se comprobó, y ya no más que eso.** El plegado decía que los datos «no deberían pasar» por el seed, que es un condicional donde hay un hecho: pasan cuando una conexión no consigue camino directo, y pasan cifrados, porque el secreto de la red lo genera el host y el seed no lo recibe jamás. El aviso decía que uno malicioso puede «intentar capturar información entre los participantes», y eso no se sostiene: lo que puede es anotar IP públicas y con quién se junta cada una. Lo de dentro de la sala no lo lee. El aviso son DOS frases y ninguna es de relleno: lo que puede hacer uno modificado, y hasta dónde llega. Estuvo en cuatro renglones, contando además lo que el seed de este repositorio no guarda y con quién se junta cada IP, y cuatro renglones justo encima del botón es donde menos se lee. Todo eso está en `kanpachi-seed.md`, entero y con lo medido, a un enlace de distancia.
- **«Más información» lleva a `kanpachi-seed.md`**, un documento del repositorio, en inglés como `kanpachi-protection.md` porque se enlaza desde fuera. Cuenta qué guarda el registro —con el volcado real de su fichero de estado—, cuándo pasa tráfico por el seed y por qué sigue siendo ilegible para él, qué podría hacer distinto uno modificado, y el hueco del vestíbulo que sigue abierto.
- **No hay «no volver a preguntar».** El nombre puede ser distinto cada vez, así que recordar un sí de ayer sobre un servidor no dice nada sobre el que trae el código de hoy. El momento en que ese recuerdo valdría algo es justo el momento en que dejaría pasar a un desconocido sin que nadie lo lea.
- **El nombre de la sala se edita en los dos sitios y es el mismo dato.** Lo que se escribe en la portada se ve en el diálogo y al revés. Obligar a cerrar el diálogo para cambiar una letra sería mandar a salir de la pregunta que dice si confías.
- **Y lo lleva TODO camino que abra una sala, no solo el diálogo.** El campo de la portada no estaba escribiendo el borrador —el sentido contrario sí, que es lo que hacía parecer que estaban atados—, así que el diálogo enseñaba la sugerencia sobre un nombre recién escrito. Los otros dos caminos tenían su propio literal: el que sigue tras escribir la contraseña del servidor, que no vuelve a pasar por el diálogo, y «Crear la sala sin juego» del selector. Los tres leen el borrador, y la sugerencia es lo que queda cuando nadie escribió nada.

## Estados del sistema en la UI

| Estado del daemon | La UI muestra |
|---|---|
| Resolving / Connecting | Spinner con "Buscando la sala..." |
| Connected | Lista de miembros, todo normal. Todos llegan directo |
| Degraded | Banner ámbar: "Alguien llega por el relay, la partida va más lenta", con ese miembro en ámbar en la lista |
| Reconnecting | Banner: "Reconectando..." (tras suspender o cambiar de red) |
| Idle | Pantalla A, con el motivo de la salida si hubo uno |

**`Degraded` no dice "reintentando", y antes lo decía.** El texto viejo era "Conexión inestable, reintentando", y las dos mitades eran falsas: ni la conexión está inestable ni hay nada reintentándose, que es literalmente el estado de al lado. Degradado es que el túnel está entero y alguien llega por el relay del seed. Nombrar el relay es lo mismo que hacen los puntos ámbar de la lista de miembros, y sirve para lo mismo: que nadie culpe al juego de una latencia que es de la red.

Por eso la tabla ya no tiene una fila "Connected (relay)": **es un estado que no existe.** Con alguien llegando por relay el estado ES degradado, porque el estado se calcula de esa misma tabla de miembros. El punto ámbar del miembro dice QUIÉN, y el banner dice que lo hay: el mismo dato a dos niveles de detalle, sin dos fuentes que puedan discrepar.

**`Reconnecting` está acotado a diez minutos.** Pasado ese plazo se sale de la sala, se cierran los puertos y se revierten los ajustes, con el texto de "la conexión con la sala no volvió". La ruedita nunca es eterna, y eso vale escribirlo: una ruedita sin final es la forma más común de que una app mienta.

### El registro caído se avisa en la portada, antes de que nadie escriba nada

Desde que crear y entrar fallan rápido sin registro, no tenerlo es la diferencia entre poder usar Kanpachi y no poder. Y las dos operaciones que lo descubren son justo las que alguien lanza **después** de elegir un juego y escribir ocho caracteres. Se puede saber antes, con la pantalla todavía vacía, así que se dice ahí:

> **El servidor de encuentro no responde**
> Es la máquina por la que las salas se encuentran, así que ahora mismo no se puede crear ninguna ni entrar a una. No hay nada que hacer de tu lado: en cuanto vuelva, esto se va solo.

Cuatro decisiones sobre ese cuadro:

- **No lleva botón, y lo dice.** No hay nada que pulsar, se cura solo en cuanto el registro vuelva, y el aviso desaparece con la siguiente ronda del latido. Un botón que no arregla nada enseña a ignorar los botones.
- **Es advertencia, no error.** No falló nada de esta máquina.
- **Va entre el aviso de servicio caído y las alertas de exposición.** Es el orden de lo que impide usar Kanpachi: sin servicio no hay nada, sin registro no se abre ni se entra a ninguna sala, y las alertas describen una máquina que sí funciona. Los dos últimos se pintan a la vez cuando toca, porque hablan de cosas distintas.
- **No es una alerta de exposición.** Ese conjunto es cerrado y son hallazgos de que la máquina quedó alcanzable. Meterlo ahí diría que se abrió algo cuando lo que pasa es que no se puede abrir una sala.

**No cierra Kanpachi, a diferencia del aviso del adaptador virtual.** Aquel apaga la app al aceptar, porque un almacén de drivers roto necesita que alguien toque la máquina. Este se arregla solo, y cerrar la ventana por algo que se cura sin intervención es quitarle a la persona el sitio donde va a ver que ya se curó.

### Un enlace muerto se tira, y antes se guardaba

El daemon corta una conexión ociosa a los diez minutos. Para esta ventana ese **no es el caso raro sino el normal**: quien mira su sala, se va a jugar una partida y vuelve, encuentra el enlace ya cortado.

Cuando eso pasaba, la ventana rompía las esperas en vuelo y **nada más**. El cliente seguía pareciendo vivo, así que el conector, que memoriza el que está en uso, seguía entregando el mismo cadáver; y el transporte no se cerraba, así que quedaban en pie el hilo que atiende el pipe, el handle y el evento de parada. Uno de cada por corte.

Lo que se veía desde fuera es lo peor de las dos mitades: **la ventana congelada con el estado de antes dibujado, sin decir que había dejado de hablar.** Medido el 2026-08-09 en el bundle portable: la interfaz supo que el enlace estaba muerto a las 15:31:26 y siguió diecisiete minutos en pantalla sin pedirle nada al daemon, hasta que el proceso se cayó.

Ahora un enlace perdido marca el cliente como muerto y cierra su transporte, y el conector comprueba lo que memorizó antes de entregarlo. La comprobación vive en quien memoriza y no en un aviso del cliente, para que no haya un cable que alguien pueda olvidarse de conectar.

### Hay una versión nueva

Una línea en la barra de estado, a la izquierda del adaptador: **«Versión v0.1.5 disponible»**. Al pulsarla se abre la página de publicaciones en el navegador. Eso es todo lo que hace.

**La página de publicaciones, y no la de descarga de un servidor.** Antes era la segunda, con un servidor compilado dentro del binario, y ese servidor dejó de significar nada: el registro es de cualquiera ahora y no es de donde salió esta copia. Lo que sí es cierto de una compilación es el canal por el que se publicó.

La tarjeta de Configuración lleva al mismo sitio, y su botón lo dice: con una versión nueva conocida deja de ofrecer «Buscar», que ya no puede contestar nada distinto, y pasa a ofrecer **«Descargar»**.

**Kanpachi no se actualiza solo, y esto no lo cambia.** El autoupdate está aparcado en `07-futuro.md` detrás de la firma de código, y con razón: lo que instalaría es un servicio que corre como SYSTEM reemplazando su propio binario por una descarga sin firmar. Mientras eso no exista, lo máximo honesto que puede hacer la ventana es decir que hay algo nuevo y llevar a la página. Un botón que dijera «Actualizar» prometería otra cosa.

**Pregunta cuando se lo piden, y en ningún otro momento.** Preguntaba tres veces sola —al arrancar la ventana, al abrirse una sala y al cerrarse—, y eso valía mientras la pregunta iba al seed, que era uno solo, compilado, con la respuesta cacheada para todo el mundo. Desde que va al canal de publicación la cuenta cambia: la cuota sin autenticar de GitHub son sesenta por hora **por IP**, que en una casa comparten todos, y varias preguntas por sesión y por máquina no caben ahí. Ahora hay un botón en Configuración, y quien lo pulsa gasta una de esas sesenta.

**Cuando encuentra una, deja de preguntar para siempre.** El número se guarda en disco junto al nombre y el tamaño de ventana, y a partir de ahí el aviso está puesto sin volver a salir a la red: una versión publicada no se despublica, así que la segunda respuesta solo puede ser la misma que la primera. Y guardarlo es lo que hace que el aviso sobreviva al reinicio, en vez de ser un cartel que solo existe mientras haya red.

Lo que lo borra no es un plazo, es llegar: al arrancar se compara lo guardado con la versión que corre, y en cuanto deja de ser mayor se olvida. O sea, el día que alguien instaló.

**A quién le pregunta: al canal de publicación.** Le preguntaba al seed, y eso se sostenía cuando el seed venía compilado: era uno solo, sabía la respuesta para todo el mundo y ninguna copia salía a internet por su cuenta. Un registro es de cualquiera ahora, así que preguntarle qué versión de Kanpachi hay es preguntárselo a la máquina de un tercero sobre el binario que corre en la tuya. Lo que se paga a cambio se dice entero: la consulta la hace cada máquina, y quien publica ve su IP. Por eso es a pedido y no automática.

**Un build sin versión no avisa de nada.** El número lo escribe el empaquetado desde el tag; compilado a mano queda en `dev`, que no se compara con nada, y entonces ni se hace la petición. Quien compiló el binario no necesita que lo manden a bajar un instalador.

**La advertencia de que instalar cierra la sala vive en el tooltip**, no en la línea. La línea tiene que caber al lado del adaptador y leerse de un vistazo; lo de la sala hace falta antes de PULSAR, no antes de leer, así que espera al puntero encima. El instalador lo vuelve a decir, y ahí sí bloqueando: ver `04-flujos-y-configuracion.md`.

### La esquina de la barra de estado lleva al servidor

Abajo a la derecha hay un dato y sólo uno: **con sala**, el adaptador virtual y tu dirección dentro de ella; **sin sala**, el servidor en el que se abrirían tus salas. Nunca los dos, porque es una línea y llenarla de datos la convierte en ruido que nadie lee.

**Sin sala esa zona se pulsa y lleva a la pantalla D.** Es el único sitio de la app donde el servidor está escrito siempre, y no llevaba a ninguna parte: cambiarlo pedía abrir el menú de cuenta, entrar en Configuración y encontrar la tarjeta. La zona entera responde, de borde a borde y con el alto completo de la barra, y se marca al pasar el ratón por encima: un objetivo de doce píxeles de alto que no se anuncia es un objetivo que hay que apuntar.

**Con sala NO se pulsa**, y esa asimetría es el punto: ahí no hay ningún servidor escrito. Llevar desde un adaptador y una dirección a la pantalla de cambiar el servidor sería mandar a alguien a otra cosa que la que está mirando.

**El globo explica qué es, en una línea, tras medio segundo de ratón encima.** El nombre solo no dice qué es esa máquina: `kanpachi.accentio.dev` ahí abajo se lee como «a dónde estás conectado», y quien lo mire con la sala de otra persona abierta se llevaría la idea contraria. La espera es lo que separa a quien lo está mirando de quien pasa el ratón camino de otro sitio.

## Bandeja del sistema

Cerrar la ventana no cierra la sala: el daemon la sostiene. Queda un icono en la bandeja con tres elementos: estado (color), "Abrir Kanpachi", "Salir de la sala". Nada de menús profundos.

### El icono parpadea mientras hay sala

Alterna cada 900 ms entre el icono normal y el mismo con un triángulo de play. Es lo que avisa de que hay una sala funcionando sin abrir nada, y vale igual siendo anfitrión o invitado: lo que se mira es que haya sala, no qué papel se tiene.

**Windows no tiene iconos de bandeja animados.** Se anima repitiendo `Shell_NotifyIcon` con `NIM_MODIFY` y otro `hIcon`, que es lo que documenta Microsoft y lo que `tray_manager` hace por debajo. Los dos cuadros son assets declarados, porque el plugin resuelve la ruta contra `data/flutter_assets`.

**El icono de la barra de tareas NO parpadea, y no es un olvido.** El `setIcon` de `window_manager` carga dos iconos con `LoadImage` y no destruye ninguno, y `WM_SETICON` no se queda con la propiedad. Medido el 2026-08-10: cada icono cargado de archivo cuesta un handle de USER y unos tres de GDI, y solo los libera `DestroyIcon`. A este ritmo serían más de siete mil handles por hora contra un tope de diez mil por proceso, o sea la ventana quedándose sin handles a media partida. Hacerlo pediría escribirlo en el runner de C++, cargando los dos iconos una sola vez, y eso está en `07-futuro.md`.

Los dos cuadros duran lo mismo a propósito, y las dos duraciones son constantes separadas: subir la del play y bajar la del quieto convierte el parpadeo en un latido, que cansa menos en una partida de tres horas. Está a un número de distancia si molesta.

## Errores como frases accionables

| Situación | Texto |
|---|---|
| Código con formato inválido | "Ese código no parece completo. Son 8 caracteres, revisa que se copió entero." |
| Sin respuesta de semillas | "No hay conexión con el servidor de encuentro. Revisa tu internet, si persiste avisa en el grupo." |
| UDP bloqueado (según Diagnostics) | "Tu red bloquea el tráfico del juego (UDP). En redes de oficina o universidad suele pasar. Vas a ir por relay, con más latencia." |
| Versión incompatible | "Tu versión de Kanpachi es vieja para esta sala. Pide el instalador nuevo en el grupo." |
| Sala sola por mucho rato | "Llevas 10 minutos solo en la sala. ¿El código llegó bien al grupo?" |
| MTU sospechoso tras el sondeo | "Tu conexión maneja paquetes más chicos de lo normal. Ajusté la red para eso. Si el juego conecta y se queda cargando, avisa." |
| Conflicto de rango detectado | "Tu red de casa usa el mismo rango que Kanpachi. Cambié el nuestro para no romperte internet." |
| Ajustes revertidos por Windows | Sin texto. Se reaplican solos y en silencio. Al usuario no le interesa saber que Windows le borró una métrica |
| El túnel no volvió en diez minutos | "La conexión con la sala no volvió. Kanpachi lo intentó durante diez minutos y cerró todo lo que había abierto. Vuelve a pegar el código cuando tengas red." |
| Reglas propias alteradas y repuestas | Sin texto. Se reponen solas, igual que los ajustes del adaptador |
| Reglas propias alteradas tres veces seguidas | "Algo está borrando las reglas de Kanpachi. Suele ser un antivirus. Mientras pase, la sala puede no funcionar." |

Regla de microcopy: cada error dice qué pasó, qué significa para el usuario y qué hacer, en ese orden, en español coloquial. Jamás un código de error a secas.

### Los cuadros que enseña el daemon, sin pasar por la ventana

Hay textos visibles que **no los pinta Flutter**. Los enseña un cuadro de diálogo del sistema, y existen para los casos en que la ventana es justo lo que no se puede usar.

**Cuál se usa lo decide en qué sesión corre quien avisa**, y esto no es un detalle de estilo. El lanzador y el bundle portable corren en la sesión del usuario, así que les sirve un `MessageBox` normal. El daemon vive en la **sesión 0**, donde no hay escritorio: ahí un `MessageBox` dibuja en una estación de ventanas que nadie mira y se queda esperando para siempre un Aceptar que nadie puede pulsar. Por eso el daemon usa `WTSSendMessageW`, que es la vía documentada para que un servicio le hable a quien está en la máquina.

| Cuándo | Quién lo enseña | Espera Aceptar |
|---|---|---|
| El lanzador falló y no hay consola donde escribir | el lanzador, `MessageBox` | sí, es modal |
| El bundle portable no pudo arrancar | el bundle, `MessageBox` | sí, es modal |
| Esta máquina no puede crear el adaptador virtual | el daemon, `WTSSendMessageW` | **sí, hasta 5 minutos** |
| La interfaz se cayó cuatro veces seguidas | el daemon, `WTSSendMessageW` | **sí, hasta 5 minutos** |

Los dos primeros esperan por lo que son: un `MessageBox` es modal y devuelve qué botón se pulsó, así que el proceso termina cuando la persona ya leyó.

**Los dos del daemon esperan a propósito, y es lo que los separa de un aviso cualquiera.** Los dos ANUNCIAN el apagado de Kanpachi, que ocurre en la línea siguiente. Un cuadro que aparece en el mismo instante en que todo se cierra se lee como que reventó. La espera es además el único rato que le queda a una partida en curso. El plazo de cinco minutos existe porque puede no haber nadie delante, y una espera infinita dejaría una goroutine colgada para siempre.

**Cuatro caídas y no tres**, que es lo que ese texto decía hasta el 2026-08-11. El tope es `maxRelaunches = 3` y la comparación es `seguidas > maxRelaunches`: tres caídas gastan los tres relanzamientos concedidos y la cuarta ya no tiene ninguno. Lo fija `TestCuatroCaídasRápidasApaganElDaemon`.

El texto del adaptador virtual se arma en el momento y no es fijo. Lleva lo que dijo el driver, capturado con `WintunSetLogger`, y lo que dijo Windows, y el consejo cambia según el código: acceso denegado manda a permisos, `0xCB` manda a revisar `DevicePath` con el comando escrito. El detalle está en `03-arquitectura.md`, en la sección del adaptador del motor, y la decisión en `02`, punto 32.

### Una acción que el usuario pidió y no ocurrió

Los de la tabla de arriba son cosas que Kanpachi observó solo. Esto es lo otro: crear la sala, entrar, cambiar el juego, expulsar, renovar el código, renombrar, salir, reponer la protección, guardar un perfil. **Antes ninguna de esas podía fallar de forma visible**, y las dos maneras en que fallaban se ven igual en pantalla: la ruedita se para y nada cambia. Quien mira no puede distinguir "falló" de "funcionó y la pantalla está vieja", así que vuelve a pulsar, que es exactamente lo que no puede pasar después de algo que pudo ejecutarse a medias.

El aviso tiene la forma de siempre y un tono nuevo, `error`: el acento tirado hacia el rojo. **Es el único tono que rompe la regla de "nunca rojo"**, y la rompe con motivo. Los otros tres hablan de cosas mejorables que Kanpachi encontró; este habla de una orden que falló, y ahí sí hay alguien esperando y algo que reintentar.

El título lo pone la ACCIÓN y la explicación el código:

| Acción | Título |
|---|---|
| Crear sala | "No se pudo abrir la sala" |
| Entrar con un código | "No se pudo entrar a la sala" |
| Cambiar o cerrar el juego | "No se pudo cambiar el juego" |
| Expulsar | "No se pudo expulsar" |
| Renovar el código | "No se pudo renovar el código" |
| Renombrar | "No se pudo cambiar el nombre" |
| Salir de la sala | "No se pudo salir de la sala" |
| Reponer la protección | "No se pudo reponer la protección" |
| Guardar un perfil | "No se pudo guardar el perfil" |
| Salir de Kanpachi | "No se pudo cerrar Kanpachi" |

Son frases distintas porque son cosas distintas, y quien lee solo se preocupa por lo segundo: `unavailable` es el mismo código para "no se creó la sala" y para "no se renovó el código", y esas dos noticias no se parecen en nada. Un genérico "algo salió mal" es el mensaje que enseña a dejar de leer los mensajes.

**Cuando el daemon ni contestó, la frase es otra:** *"El servicio de Kanpachi no contestó, así que no llegó a intentarse. Vuelve a probar."* Se separa de todos los códigos a propósito. Aquellos son el daemon diciendo que no, y este es el daemon no estando; solo en el segundo caso se sabe que no ocurrió nada a medias, y saberlo es lo que hace seguro reintentar.

El aviso va anclado abajo, sobre la pantalla y bajo los diálogos. Anclado y no empujando el contenido: una acción que falla no puede mover el botón que la persona está a punto de volver a pulsar.

### "Ver detalles", y el modo verboso que lo enciende

Debajo del aviso hay un botón que abre los pasos de lo que falló, con su reloj, quién dio cada paso y cuánto tardó, más la línea cruda del daemon. Los pasos van primero y el error al final, y ese orden es el punto: la línea de error dice dónde se paró, y los pasos dicen hasta dónde llegó. Casi siempre es lo segundo lo que dice a cuál de los dos hay que ir a mirar.

El mismo panel se enseña **mientras** se crea o se busca una sala, debajo de la ruedita, y por lo mismo: esperar cuarenta segundos y estar colgado se ven igual desde fuera.

**Lo enciende un ajuste, no la compilación.** Empezó siendo `kDebugMode` a secas, o sea una constante de compilación que podaba del binario publicado el panel, el sondeo y la conexión extra. Más barato, e inservible justo en la situación que importa: una sala que no abre en la máquina de otra persona, corriendo el binario que se reparte, donde esos ocho pasos son el diagnóstico entero y recompilar no es una opción.

Así que ahora es una casilla en Configuración, con el valor de partida atado al tipo de compilación: encendida mientras se desarrolla, apagada en el producto. Lo que cuesta encenderla, dicho claro: una segunda conexión al daemon y una consulta un par de veces por segundo **mientras se abre una sala**, y nada el resto del tiempo. Apagada no se pide nada, y el botón de detalles no se dibuja, que también es lo correcto: sin sondeo nadie recogió los pasos, así que abriría sobre nada.

Con el panel abierto, la lista de pasos **tiene su propio scroll** y se pega al último. Los pasos no se sabe cuántos van a ser y la pantalla de espera comparte sitio con la ruedita y su nota: medido, una creación que llegaba al motor desbordaba la pantalla 116 píxeles por abajo, y lo que un desborde por abajo esconde es el final de la lista, que es justo lo que se está esperando. El encabezado con la operación y su reloj queda fuera del scroll. Si quien mira sube a leer un paso anterior, deja de seguirse solo hasta que vuelva al final.

Cómo se piden esos pasos está en `docs/03`.

### Configuración, detrás del engranaje

Cuelga del menú de cuenta, en un engranaje al lado de "ENTRAS COMO", y de ningún otro sitio. **Nada de lo que hay dentro hace falta para jugar**, y un botón de ajustes en la portada diría lo contrario: que hay algo que configurar antes de empezar. Quien tiene un problema concreto sabe buscar.

Son tres, y no hay más porque el resto ya lo decide alguien mejor: el firewall lo manda el daemon, el juego se elige dentro de la sala, y el nombre tiene su propia pantalla porque se pide en el alta. La cuarta tarjeta no es un ajuste: es el botón de buscar versión nueva, que vive acá porque acá es donde alguien viene a preguntar por su copia.

| Tarjeta | Qué hace | Dónde vive el valor |
|---|---|---|
| Servidor de encuentro | enseña el nombre en monoespaciada, y lleva a la pantalla D para cambiarlo | el daemon, en disco, junto al resto de su estado |
| Arrancar Kanpachi con Windows | cambia el servicio entre arranque automático retrasado y a demanda. **No se pinta en portable** | el Administrador de servicios |
| Verificar actualizaciones | dice qué versión corre, pregunta al pulsar, y con una nueva conocida lleva a bajarla | el disco, para que el aviso sobreviva al reinicio |
| Mostrar detalles del servicio Kanpachi | enciende el panel de pasos y el botón de detalles. **En portable arranca ENCENDIDO** | las preferencias de esta ventana |

**La tarjeta del servidor dice para qué sirve el servidor, y no lo que hace la app con él.** «Es donde se abren tus salas» describe un ajuste; lo que hace falta saber es qué máquina es esa y hasta cuándo interviene: presenta entre sí a los que entran con el código, hasta que la sala se levanta, y desde ahí el juego va directo entre los miembros. Se dice también la excepción, porque existe y se mide: la conexión que no consiga camino directo pasa por él. Lo que ese servidor ve de ti —tu IP pública, la de todo el que entre— se cuenta entero en el diálogo de confianza, que es donde se decide, y no acá, que es donde se mira.

**Las cuatro tarjetas llevan el mismo aire por dentro que las de la sala**, y lo llevan de un token compartido. Estas nacieron sin ninguno, con el texto y el botón tocando el borde, mientras las de la sala tenían dieciocho por dieciséis escritos a mano en cada sitio: dos maneras de que la misma caja se vea distinta según qué pantalla la dibuje. El aire de fábrica lo pone quien usa la tarjeta y no la tarjeta, porque hay tarjetas que a propósito no lo quieren, como una lista cuyos separadores llegan al borde.

**El servidor va primero, y es el único de los tres ajustes que decide algo del producto**; los otros dos son sobre la app. En una copia portable es además el primero de todos, porque «Este equipo» no se dibuja ahí. Es también el único que se RELEE al entrar: no viaja en el latido, así que lo que hubiera en memoria puede ser de hace una hora, y esta es justo la pantalla donde alguien viene a mirarlo.

**El password del servidor NO está acá.** Se pide cuando abrir una sala falla porque el servidor lo pide, y en ningún otro momento: casi ninguno lo pide, y ofrecerlo en Configuración le cobraría a todo el mundo el roce de un caso raro. Ver la pantalla E.

**En una carpeta portable los dos cambian, y lo decide el marcador en disco, no una bandera de compilación.** `PipeNames.isPortable` mira si `kanpachi.portable` está junto al ejecutable, que es lo mismo que ya deciden el pipe, el token y el directorio de datos. Así un solo `kanpachiui.exe` sirve para el producto instalado y para el bundle portable; con `--dart-define` harían falta dos builds distintos y la posibilidad de cruzarlos.

**El marcador se lee en `main()` y baja por el registro de dependencias**, hasta `ShellState.portable`. La pantalla de configuración no lo pregunta ella misma, y el motivo es un candado: `PipeNames` vive en `infra`, y `import_purity_test` prohíbe que una pantalla importe infra. La primera versión lo hacía, el candado se puso rojo, y ese rojo llegaba hasta el workflow de publicación, que corre `flutter test` antes de armar el instalador. Es exactamente para lo que están los candados.

Del arranque con Windows **se oculta la tarjeta entera**, no solo el interruptor: en portable no hay servicio registrado que Windows pueda levantar al encender, así que la opción no existe. Un interruptor apagado y gris diría dos cosas falsas —que la opción existe, y que hoy no se puede—, y una tarjeta "Este equipo" con nada debajo es peor que ninguna. Tampoco se le pregunta nada al daemon: no hay qué leer, y preguntarlo dejaría un error en pantalla que no es un error.

El de contar los pasos arranca encendido, y es un default, no una imposición: se apaga desde esta misma pantalla y la elección se recuerda. Portable es lo que alguien corre cuando el instalado no es opción —un amigo probando diez minutos, o una máquina donde algo va mal—, y en los dos casos los pasos SON el motivo por el que se está corriendo.

**El arranque con Windows no se guarda de este lado.** Se lee del Administrador de servicios cada vez que se entra a la pantalla, y se escribe pidiéndoselo al daemon, que ya es SYSTEM. Una copia acá serían dos verdades para un mismo hecho, y la que se enseñaría es la que no manda: cualquiera pudo cambiarlo desde `services.msc` entre una visita y la siguiente. Lo que vuelve tras cambiarlo es lo que quedó puesto de verdad, releído, y no lo que se pidió.

Mientras no se sepa la respuesta, el interruptor va apagado y sin poder tocarse, con el motivo debajo. Dibujarlo en "no" sin haberlo leído sería contestar con una suposición en la única pantalla que existe para contestarlo. Es lo que pasa con un daemon de consola, donde no hay servicio registrado que consultar. En portable ya no se llega a ese estado: la tarjeta no se pinta.

**Apagarlo no desinstala nada, y el texto lo dice ahí mismo.** Es lo primero que alguien teme al ver ese interruptor, y ese miedo es lo que hace que no lo toque quien lo necesita. El servicio sigue instalado y Kanpachi arranca igual al abrirlo; lo único que cambia es que Windows deja de levantarlo solo.

### La pantalla SIGUE a la sala, no la supone

La navegación era de ida y nada más: se entraba a la sala porque el usuario pulsó crear, y a partir de ahí la pantalla y la sala del daemon coincidían por costumbre. Bastaba salirse de esa costumbre para romperlo, y salirse era fácil:

| Qué hacía el usuario | Qué pasaba |
|---|---|
| Crear una sala, entrar a Configuración, volver | portada **sin sala**, con el daemon dentro de una |
| Pulsar crear otra vez | "ya estás en una sala", y nada podía desbloquearlo |
| Un invitado saliendo de la pantalla de sala | lo mismo |
| El host cerrando la sala desde otra parte | el invitado no se enteraba nunca |
| Levantar el daemon con la ventana abierta | seguía diciendo "sin servicio" hasta cerrar y abrir la ventana |

Ahora el latido de `docs/03` trae la sala de verdad y la pantalla la sigue, en los dos sentidos:

- **Aparece una sala** estando en la portada o en la bienvenida: se va a la sala. Cubre volver de Configuración, cubre reanudar la sala del arranque anterior, y cubre que la sala la haya abierto cualquier otra cosa.
- **Desaparece la sala** estando en una pantalla que la necesita: se va a la portada.

**No arrastra a nadie fuera de donde eligió estar.** Configuración, el selector de juego y la exposición se ven con sala y sin ella, así que una sala que aparezca mientras alguien mira los ajustes no lo saca de ahí. La lista de pantallas desde las que sí se salta es corta y explícita, porque una pantalla nueva no debería empezar arrastrando a nadie por omisión.

### Volver es una operación sobre el CAMINO, y ahora hay camino

Cada flecha del encabezado llevaba escrito su destino a mano, y ese destino solo acertaba si se había llegado por donde quien lo escribió imaginaba. Configuración llegó a tener dos versiones del mismo error: primero "siempre a la portada", después "a la sala si hay sala" — que acierta viniendo de la sala y falla viniendo del selector de juego, del catálogo o de un enlace.

**El caso que lo delató:** un host dentro de su sala recibe un código, la pantalla del enlace se pone delante, y pulsa Cancelar precisamente para NO salirse de lo suyo. La flecha lo dejaba en la portada.

El shell guarda ahora el camino recorrido y `back()` lo desanda. Tres detalles que hacen que no se degrade:

- **Ir a donde ya se está no apila.** Sin esto, el latido que reafirma la sala metería una copia de la sala detrás de sí misma, y la flecha siguiente se quedaría a mitad de camino.
- **Volver a una pantalla que ya está en el camino lo DESENROLLA hasta ella.** Sala → ajustes → sala → ajustes no crece sin fin, ni cuenta un viaje que nadie hizo.
- **Al cerrarse la sala se poda el camino que llevaba a ella.** Una flecha que apunta a una pantalla que ya no se puede dibujar es una flecha que no hace nada visible, que es peor que una que no está.

### Con sala abierta, la portada no es un sitio donde se pueda estar

La portada ofrece dos cosas —crear una sala y entrar a otra— y las dos contestan `busy` mientras haya una. Con una sala abierta es una pantalla entera cuyos botones no hacen nada, con la sala de quien la mira escondida detrás.

Se llegaba a ella por varios caminos, y cada uno se venía arreglando por su lado: una flecha mal apuntada, cancelar un enlace, un "cerrar la sala" que falló. Ahora lo decide el único sitio que decide qué se ve: **mientras el daemon diga que hay sala, la pantalla de la sala gana.** Se comprueba después del enlace, que sí se ve con sala abierta y a propósito.

Consecuencia sana: salir de la sala ya no navega. Se le pide al daemon y se espera; cuando la sala se va de verdad, el oyente lleva a la portada. Un "salir" que falla deja al usuario en su sala en vez de en una portada que no acepta nada.

### La auditoría del firewall NO va con el latido

El aviso de reglas ajenas —«este programa tiene una regla abierta», roja cuando es control remoto— sale de barrer el almacén de reglas ENTERO de Windows buscando el ejecutable del juego y las herramientas de escritorio remoto. En una máquina real son **1009 reglas revisadas**, y cada revisión es una ristra de llamadas COM al servicio del firewall.

Se pedía con cada vistazo a la sala, o sea **cada dos segundos**, porque el comentario que lo defendía se escribió cuando no había latido y «cada refresco» quería decir cuando alguien entraba a una pantalla. Con latido, eso costaba de tres formas y las tres se midieron o se sufrieron:

- **CPU en máquinas viejas**, que son justo las que juegan a esto.
- **La forma que un antivirus marca.** Un proceso que enumera el almacén de reglas del firewall sin parar se parece a lo que un antivirus está entrenado para detener.
- **El canal con el daemon**, que es uno solo y se atiende de a una petición. Un barrido lento encola detrás lo barato —`status`, el enlace pendiente— hasta que revientan su plazo de diez segundos, y la app pinta «sin servicio» con el daemon vivo. Medido: barridos de hasta 5,9 s con la máquina en reposo, sobre una cadencia de 2 s.

Ahora se barre en cuatro momentos, y en ninguno más:

| Cuándo | Por qué ese |
|---|---|
| Al entrar a la pantalla de la sala | Es donde el aviso se lee. Un aviso que nadie mira no hace falta que esté fresco |
| Al cambiar de juego | Cambia el ejecutable que se busca, así que lo anterior deja de significar nada |
| Al entrar alguien nuevo a la sala | Es cuando una regla abierta pasa de ser un dato a ser una puerta con alguien delante. Solo al ENTRAR: que alguien se vaya no abre nada, y barrer en cada salida convertiría una sala vaciándose en una ráfaga |
| Cada dos minutos | La red que cubre lo que no es ninguno de los tres |

Se puede espaciar sin perder el aviso porque **estas reglas no cambian solas**: aparecen cuando alguien instala un juego o el juego se registra en el firewall, y desaparecen cuando alguien las borra. Son actos de una persona, no eventos de red. Y lo que el usuario decide sobre el aviso —dejarla puesta o desactivarla— se recuerda sin volver a preguntar: el almacén acaba de quedar como ese código dice.

### El latido no se solapa consigo mismo

El temporizador dispara cada dos segundos sin mirar si el anterior terminó, y cada latido son tres peticiones por el mismo canal, que el daemon atiende de a una. Con una llamada lenta, el segundo latido se encola detrás del primero y la cola ya no baja: las peticiones revientan su plazo y la app dice «sin servicio» sin que nada esté caído. Un latido en vuelo hace que el siguiente tick no haga nada. Saltarse un tick es gratis; encolarlo cuesta la conexión.

### Cerrar la sala no es salir de ella

El botón decía "Salir de la sala" para todos, y para el host era mentira por omisión: cuando el host se va, la sala se acaba para todos los que están dentro. Es la única acción de la app que le cambia el estado a otras máquinas sin que ellas hagan nada.

Ahora el host lee "Cerrar la sala", y **con gente dentro se pregunta antes**. Solo entonces: un host solo en su sala no le está haciendo nada a nadie, y ahí el diálogo sería una pulsación de más en el caso normal.

El diálogo enumera lo que se cierra en vez de decir "se cerrará la sala", porque lo primero se puede comprobar y lo segundo hay que creérselo: se avisa a cada miembro, se cierran los puertos del juego, se devuelven las reglas que se hubieran desactivado, se suelta la compuerta, se revierten los ajustes del adaptador, se cierra el canal y se baja la red. El daemon ya hacía todo eso en ese orden; lo que faltaba era decirlo antes de hacerlo.

**El proceso del motor no se mata**, y es a propósito: la red virtual sí se baja —medido, cero adaptadores después de salir— y el proceso hijo se queda para que abrir la sala siguiente no pague otra vez su arranque. Muere con el daemon, por el job.

### Salir y cerrar también son esperas, con su pantalla

Son cuatro pantallas de espera y no dos: crear, entrar, salir y cerrar. Las dos últimas llegaron después, y su ausencia era un fallo de la misma clase que el de crear sin botón de cancelar.

**Salir tarda lo que tarda bajar la red cifrada**, que es esperar a que otro proceso termine, más cerrar los puertos, restaurar las reglas ajenas suspendidas, soltar la compuerta, revertir los ajustes del adaptador y cerrar el canal. Sin pantalla, la sala se quedaba quieta con sus botones vivos durante esos segundos, que se ve exactamente igual que un botón que no hizo nada, e invita a pulsarlo otra vez.

| Rol | Título | Qué dice debajo |
|---|---|---|
| Invitado | «Saliendo de la sala…» | Cerrando los puertos que se abrieron, devolviendo las reglas que se habían suspendido y bajando la red de la sala |
| Host | «Cerrando la sala…» | Lo mismo, empezando por avisar a los miembros |

**Son dos textos y una sola operación**, y la distinción es la misma que ya hacía el botón que las dispara: al host se le cierra la sala para todos, y decirle «saliendo» mentiría por omisión sobre lo que les pasa a los demás.

**Ninguna de las dos lleva cancelar, y eso es una decisión y no un olvido.** Cortar un desmontaje a la mitad deja exactamente el estado que salir existe para deshacer: reglas puestas para una sala que ya no está. La salida de esta espera es dejarla terminar, que son segundos.

El panel de pasos funciona igual que en las otras dos, con la misma narración del daemon: quién cierra qué y cuánto tardó cada cosa. Antes de esto el daemon no anotaba ni un paso al salir, así que una salida lenta no se podía mirar por dentro.

### Cancelar la espera

Las dos esperas largas que CONSTRUYEN algo llevan botón de cancelar, y **antes solo lo llevaba una**. Crear una sala no ofrecía salida ninguna, que era justo al revés de lo que hacía falta: es la que levanta un motor, toma dirección en dos adaptadores y escribe reglas, o sea la que más deja puesto mientras corre. La única salida de un minuto de espera era esperar el minuto.

Y el que sí existía no cancelaba. Salía de una sala en la que todavía no se había entrado y navegaba a la portada: la pantalla se iba y el daemon seguía, con el motor arriba y las reglas puestas por una sala que la app ya no creía estar abriendo.

Ahora los dos mandan **la misma orden**, y el daemon deshace lo que alcanzó a hacer. Cómo, en `docs/03`.

**La pantalla vuelve a la portada en el acto, sin esperar la respuesta.** Lo que la persona pidió es dejar de esperar, y la operación tarda unos segundos en enterarse: dejar la ruedita mientras tanto hace que el botón parezca roto e invita a pulsarlo otra vez.

**Y no sale ningún aviso de error.** El daemon contesta una operación cancelada con un fallo, correctamente, y pintar el cartel rojo encima de un botón que la persona acaba de pulsar es ruido. Se traga ese fallo y solo ese.

### Un código que no existe

Se sabe **en menos de un segundo**, y antes tardaba cerca de un minuto: había que levantar el motor, entrar a un vestíbulo vacío y agotar los reintentos del canal para llegar a "no se pudo". El texto tiene que servir para las dos causas que dan la misma respuesta, porque desde acá son indistinguibles:

> Ese código no existe. Puede estar mal copiado, o la sala se cerró y el host tiene que pasarte uno nuevo.

**El registro sin contestar es OTRO mensaje, y esa separación es el punto.** Los dos paran el ingreso en el primer segundo, y lo que la persona tiene que hacer es lo contrario en cada caso:

> El servidor de encuentro no responde, así que ahora mismo no se puede crear una sala ni entrar a una. Prueba de nuevo en un rato.

Con el de arriba hay que conseguir otro código y reintentar no cambia nada. Con este el código puede estar perfecto y lo único que corresponde es esperar. Un solo texto para los dos mandaría a la mitad de la gente a hacer justo lo que no sirve. Viajan como `no_such_room` y `no_registry`, y el mismo `no_registry` sale al intentar **crear** una sala, que falla por la misma razón.

### El tamaño de la ventana se recuerda, la posición no

Abre con 888 × 565 la primera vez y con lo que dejaste todas las demás. Es **más angosta que el ancho de contenido** (940), y eso es deliberado: ese número es un tope y no una meta, y las pantallas se acomodan solas por debajo de él, igual que hacen en cualquier ventana sin maximizar. El alto no sale del archivo de diseño: sale de que una ventana que abre ocupando media pantalla es una ventana que hay que encoger, y encogerla es lo que nadie hace.

**La posición NO se guarda: siempre abre centrada.** Parecen la misma preferencia y no lo son. Quien agrandó la ventana la quiere grande otra vez, porque es una decisión sobre la app; dónde estaba era una decisión sobre aquel momento, o sea qué monitor había enchufado y qué más estaba abierto. Restaurarla es cómo una ventana vuelve medio fuera de la pantalla después de desconectar una pantalla, o entera dentro del monitor que ahora está apagado. Centrada siempre es aburrido y siempre funciona.

Dos detalles que se notan al usarlo: maximizar **no** cuenta como redimensionar, porque Windows reporta una ventana maximizada al tamaño del monitor y guardarlo daría una ventana del tamaño de la pantalla sin estar maximizada, imposible de restaurar. Y se escribe medio segundo después del último arrastre, no en cada fotograma.

### Cuando el daemon no puede abrir la interfaz

Ese caso no tiene pantalla donde escribirse, porque la pantalla es justo lo que no se pudo abrir. El daemon lo dice con un cuadro de mensaje en el escritorio de quien está usando la máquina, no con uno propio: corre en la sesión 0, que no tiene escritorio, así que un cuadro suyo esperaría para siempre un botón que nadie puede pulsar.

Pasa en dos momentos y con dos textos: cuando el lanzamiento falla de entrada, y cuando la interfaz se cae tres veces seguidas y se deja de insistir. Sin esos avisos, lo que queda es un servicio corriendo con nada en pantalla, que es exactamente la forma que la invariante de `docs/03` prohíbe.

**El orden de las frases es el contenido, y la primera versión lo tenía al revés.** Abría con el error crudo de Go, así que lo primero que alguien leía era una cadena de una API de Windows en inglés, encima de un cuadro que no dice qué pasó. Un cuadro así tiene cuatro cosas que decir y este es su orden:

1. Qué pasó, en una frase: Kanpachi se está ejecutando y no consiguió abrir su ventana.
2. Qué NO se rompió: si había una sala, sigue abierta. Lo que falta es la ventana.
3. Qué hacer: volver a abrirlo desde el acceso directo.
4. El detalle técnico, **etiquetado como tal**, al final y para copiar en un reporte.

La cuarta va con su etiqueta y no suelta porque los errores de ese camino son de dos clases que quien lee no tiene por qué distinguir: unos están escritos para leerse, como el del permiso del servicio, y otros son la cadena cruda de una API.

### Dónde vive este texto

En `ui/lib/core/messages/`, que es el único sitio del programa donde se escribe copy de aviso. Antes vivía repartido por las pantallas que lo necesitaban, con tres consecuencias que se notan tarde: la misma situación se explicaba distinto en dos sitios, cambiar una frase obligaba a buscarla por el árbol, y no había forma de responder la pregunta que importa, que es si hay alguna situación que el daemon sepa reportar y para la que no tengamos texto.

Son cuatro piezas con un reparto estricto:

| Pieza | Qué hace |
|---|---|
| `message_keys.dart` | Las claves del daemon espejadas en Dart: `AlertKind`, `ExitReason`, `ConnState`, `FailureCode`. Y `FailedAction`, que no viene del daemon: es qué pidió el usuario, y vive acá porque `core/messages` no puede depender de una feature sin invertir la flecha. Nada de texto |
| `app_message.dart` | `AppMessage`, el mensaje ya resuelto. Datos puros, sin widgets |
| `message_catalog.dart` | `AppMessages`, la tabla de clave a texto. No decide cuándo mostrar nada |
| `app_message_notice.dart` | `AppMessageNotice`, la clase que lo pinta sobre `AppNotice` |

**El daemon manda la clave, la UI pone el texto.** Lo decide el propio daemon en `protocol.go`: *"Códigos y no texto suelto porque la UI tiene que poder decidir qué pantalla mostrar sin leer castellano"*. El campo `detail` que acompaña a una alerta es el dato concreto y se muestra debajo, en mono y apagado; jamás sustituye al cuerpo, porque entonces el texto del producto dependería de cómo redacte el daemon.

**Que el catálogo esté completo no es disciplina, son tres candados.** Cada método es un `switch` sin `default`, así que agregar una clave deja de compilar hasta que alguien escriba su texto. `message_catalog_test.dart` comprueba que ninguna rama devuelva un texto vacío o truncado, que es lo que el compilador no puede ver. Y `message_lockstep_test.dart` lee el fuente de Go y falla si un enum de Dart deja de coincidir con la función que lo serializa, que es lo que impide que la copia a mano se quede atrás en silencio.

**Una clave que esta versión no conoce no rompe la pantalla ni desaparece:** sale como el mensaje de reserva, llevándose el detalle del daemon. El daemon y la UI se actualizan por separado, así que ese caso va a existir.

**Al catálogo va lo que avisa, no todo lo que se lee.** Errores, advertencias y motivos de salida, que son los textos que se repiten entre pantallas y los que tienen que coincidir con una clave del daemon. El texto descriptivo de cada pantalla, sus títulos, sus ayudas y sus botones, se queda escrito donde se usa: centralizarlo solo añade un salto para leer lo que ya estaba a la vista, y esta app no se traduce a otro idioma.

**Con la firma en contra, el encabezado dice «No se pudo verificar esta invitación»** y no se abre la tarjeta. La página comprueba la firma Ed25519 de la tarjeta contra la llave que el propio servidor publica, así que un registro que sirva una tarjeta que su llave fijada no respalda no consigue que se pinte nada suyo. Es un caso mudo por diseño: sin sala que enseñar, la línea dice lo único cierto, y el ID, el contador y el botón siguen ahí, porque quien decide de verdad es la app. En un navegador sin `Ed25519` en WebCrypto la tarjeta se pinta como siempre, con el «se identifica como» que no afirma haber verificado nada, y jamás con un sello de verificada.

Sin fragmento, o con una clave que no descifra, caen el nick y el nombre de la sala. El avatar vuelve a la marca de Kanpachi en vez de la inicial, y el encabezado dice "Te invitaron a una sala de Kanpachi". Quedan el contador, el ID y el botón. Es el caso de un ID dictado por teléfono, y tiene que verse deliberado y no roto.

**El aviso de seed ajeno va en el pie, no en los chips.** Se probó como un tercer chip y falló por dos motivos: empujaba la fila a dos líneas rompiendo la composición, y le repetía el dominio a alguien que ya lo tiene en la barra de direcciones. Cuando el seed no es el de Accentio, el host del pie va en ámbar y nada más. Es un dato, no una alarma.

La advertencia con peso es la de la pantalla C, que muestra el servidor siempre, lo resalta si es ajeno, y no se puede saltar. Poner una alarma en una página web que cualquiera puede servir tiene poco valor: quien monta una invitación falsa también controla lo que esa página dice de sí misma.

### Portada, en `/`

Llegar sin código no es un error del usuario, así que no se ve como uno. Es la portada del producto y tiene exactamente dos salidas.

```
┌──────────────────────────────────────────────────┐
│                   kanpachi                       │
│   Jugar en LAN con tus panas, sin abrir puertos  │
│              ni crear cuentas.                   │
│                                                  │
│   ¿TE PASARON UN CÓDIGO?                         │
│   ┌────────────────────────────┐  ┌──────────┐   │
│   │ A7K2-M9QX                  │  │  Entrar  │   │
│   └────────────────────────────┘  └──────────┘   │
│   El código no es una contraseña: te lleva a la  │
│   puerta, no te mete adentro. Quien te deja      │
│   entrar es el host, y puede revocarte.          │
│                                                  │
│   ──────────── O EMPIEZA AQUÍ ────────────       │
│                                                  │
│   ┌──────────────────────────────────────────┐   │
│   │     Descargar Kanpachi para Windows      │   │
│   └──────────────────────────────────────────┘   │
│      Windows 10 y 11 · 64-bit · un solo UAC      │
│   ────────────────────────────────────────────   │
│   • Tu router no se toca. …                      │
│   • Solo los puertos del juego. …                │
│   • Sin cuentas ni telemetría. …                 │
└──────────────────────────────────────────────────┘
```

**La descarga se adapta a la plataforma detectada, y la detección jamás bloquea.** En Windows, el botón y su línea de abajo con el único UAC. Fuera de Windows, el botón dice "Descargar el instalador de Windows" y la nota explica que se puede bajar acá para pasarlo al PC, o pedir el código y abrirlo allá. El enlace funciona en las dos, porque la detección por user agent se equivoca y equivocarse no puede dejar a nadie sin salida.

**Ni la versión ni el peso ni el hash se escriben en la página, y eso corrige un error que la dejó inservible.** Vivían en una constante `RELEASE` que alguien tenía que rellenar en cada publicación. Nadie la rellenó nunca, así que quedó vacía para siempre y la pantalla dijo "todavía no hay instalador" durante toda la vida del producto, escondiendo un botón que además apuntaba a `/descargar/kanpachi-<version>.exe`, una ruta que el seed contesta con la propia página.

El botón apunta ahora a `releases/latest/download/kanpachi-setup.exe`, la URL permanente que GitHub redirige a la última publicación. Es el mismo mecanismo que ya usa `seed/install.sh`. Publicar un tag actualiza esta página sin tocarla, y por eso el instalador se llama igual siempre: ver `04-flujos-y-configuracion.md`.

**Debajo del botón, en pequeño, la versión portable**: «o descarga la versión portable, sin instalar nada», apuntando a `releases/latest/download/kanpachi-portable.exe` por la misma vía permanente. Va en pequeño y debajo a propósito: lo que casi todo el mundo quiere es el instalador, y ofrecer dos descargas del mismo peso obliga a elegir antes de saber la diferencia. Está para quien la busca, que son dos casos concretos: probar Kanpachi sin dejar nada en la máquina, y ayudar a alguien a diagnosticar sin pedirle que instale.

**El hash vive donde se genera, en la publicación, y la página enlaza allá.** Escribirlo acá tendría el mismo problema y peor consecuencia: un hash desactualizado da por manipulado un instalador bueno, o sea que verificar pasa a ser una razón para no instalar.

Mientras no haya instalador publicado, el botón lo dice en vez de prometer un archivo que no existe.

**Una frase que NO puede aparecer acá.** El diseño original decía *"el código nunca sale de tu navegador: viaja en el fragmento del enlace y este servidor jamás lo recibe"*. Eso fue cierto y dejó de serlo con la decisión 17: el invite ID va en la ruta y el servidor lo recibe. Mantener esa frase sería mentir justo en la línea que existe para dar confianza. La reemplaza lo que sí es cierto, que el código es un ticket y la cerradura la tiene el host.

**"Entrar" es un enlace con `href`, no una navegación por JavaScript.** Dos motivos: deja el único `window.location.href` de la página para el intent `kanpachi://`, que es lo que el test de arquitectura vigila, y de paso funciona con el botón central del ratón y con "abrir en pestaña nueva". Se habilita solo cuando lo escrito tiene forma de invite ID, y con Enter en el campo hace lo mismo. Un código con forma inválida marca el campo y explica el formato; un campo vacío no se regaña.

Los tres puntos de abajo no son marketing, son las tres promesas que el resto del producto tiene que sostener: el router no se toca, solo se abren los puertos del juego activo, y no hay cuentas ni telemetría.

### Descarga

En `/download`. Versión, tamaño, y el SHA256 del instalador en monoespaciada, que es lo que permite verificar lo que bajaste. Mientras no haya instalador publicado, dice que todavía no lo hay en vez de ofrecer un botón que no lleva a nada.

**Se llamaba `/descargar` y ahora es `/download`, y la vieja sigue contestando.** El nombre está en inglés por lo mismo que el changelog y las notas de publicación: es lo que se publica hacia fuera, y es la dirección que la app escribe en su propio aviso de versión nueva. La ruta anterior no se retiró: la llevan los enlaces ya repartidos y los que están impresos en estos documentos, y una ruta vieja que deja de resolver convierte un enlace guardado en la portada sin decirle a nadie que se equivocó de sitio. Cuesta una comparación en el enrutador de la página.

### Reglas de la página

- **No se dispara el intent al cargar.** Solo con el click. Los navegadores penalizan la navegación a esquemas externos sin gesto del usuario, y una página que abre programas sola es justo lo que un desconfiado espera de un link sospechoso.
- **No se intenta detectar si la app está instalada.** No hay forma confiable, el truco del temporizador falla distinto en cada navegador y versión. El mensaje de "si no pasó nada" cubre el caso sin adivinar.
- **El fragmento es entrada hostil.** Lo controla quien manda el link. Se valida contra el alfabeto, tiene tope de longitud, y se escribe con `textContent` jamás con `innerHTML`.
- **Sin analítica, sin tracking, sin cookies, sin recursos externos.** Coherente con cero telemetría. Los logos van en línea, no como archivos aparte, así una CSP que prohíbe todo lo de fuera sigue valiendo.
- **La página nunca afirma identidad.** Ver decisión 25.
- Las tres salidas conviven sin que la página decida por el usuario: abrir, descargar, o copiar el ID a mano.
- **La versión del botón de descarga viene INCRUSTADA, y la página no pregunta nada.** El botón dice «Descargar v0.1.4» en vez de «la última versión», y ese número llega en el hueco de estado que el seed ya inyecta al servir la página.

  Preguntarle a `api.github.com` desde la página sale más barato de escribir y cuesta tres cosas: manda la IP de quien mira a un tercero, gasta la cuota de sesenta por hora **de esa persona**, que la comparte con toda su red, y obliga a abrir `connect-src` a un origen ajeno en una CSP que está cerrada a `'self'` a propósito. Con el número incrustado, la página **no consulta ninguna URL**, así que no hay dominio que configurar para que sepa dónde mirar y el `connect-src` se queda sin ningún uso que lo justifique.

  Esto lo pedía antes a `GET /api/version`, que **ya no existe**. Su único otro consumidor era `kanpachi upgrade`, que hoy le pregunta a GitHub y solo cuando alguien se lo pide, así que el endpoint se quedó sin llamadores y un endpoint público sin llamadores es superficie gratis.

  **Es un añadido, no un requisito.** El botón ya funcionaba sin esto y la nota de abajo ya manda a la publicación, donde están la versión y el SHA256. Si el seed no contesta —página abierta desde el disco, registro caído, versión aún sin resolver— se queda el texto de siempre. Por eso el registro **omite el campo** cuando no lo sabe en vez de mandar una cadena vacía: son dos hechos distintos, y "no lo sé" no se pinta.

## Lo que no existe en la v1

Pantalla de ajustes, asistente de primera ejecución, login, notificaciones push, temas, idiomas adicionales. Si un ajuste se vuelve imprescindible, nace detrás de un enlace "Avanzado" que el 95% jamás abre.

**Tampoco existe, y es a propósito:** ningún aviso, banner o automatismo disparado por abrir un juego. Kanpachi no vigila procesos, así que la UI nunca reacciona a que arrancaste algo. El juego de la sala se elige a mano y esa elección es lo único que abre puertos.
